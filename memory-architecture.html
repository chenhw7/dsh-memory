00

Overview: memory is a pipeline

Cairn (@chenhw7/dsh-memory) is not a static table — it is a loop with inflow, outflow, and decay.

Signal sensingprojector
→
LLM extractionextract
→
Safety gatescanContent
→
PersistenceKV + audit
→
BM25 retrievalrank
→
Context injectioninject
↺ Decay and sweeps recycle in the background: entries in use stay fresh, the ignored quietly step aside — then the loop begins again.

Under the hood it is seven Cordis rows: memory-store opens the storage domain and registers the ctx.memory service; tool-memory exposes the nine model-facing tools; memory-review runs auto-extraction and consolidation; memory-context owns system-prompt injection; memory-notes renders conventions and pitfalls into the project-notes section (writing nothing into your repository); memory-remote backs the memory console in Settings (remote writes denied by default); memory-root only discovers client modules. All rows share one storage domain.

The data lands in $DSH_HOME/storages/memory.json (the default host-medium backend) or $DSH_HOME/storages/memory.db (the SQLite backend) — uninstalling the plugin never deletes your memories.

WHY · WHY DESIGNED THIS WAY

Why ship as one package with zero-dependency kernels?

One npm package carries all seven rows: host services are declared as peer dependencies, provided by the DeepSeek Harness you already have — never re-installed. The retrieval, tokenization, and scanning kernels are hand-rolled with zero third-party dependencies (a recorded engineering constraint), and SQLite rides Node's built-in node:sqlite. The tarball ships prebuilt, so the install path runs no build scripts — the smaller the supply chain, the smaller the trusted surface.

01

Birth: it only learns on signal

Every user message and tool result streams through a zero-LLM-cost projection accumulator — it only recognizes three kinds of signal.

SIGNAL / 01

Explicit intent · keyword

The user asks to remember. Patterns like "记住 / 以后都 / remember that / from now on" hit and enter the candidate pool.

"Remember: this deploys on port 8080"
SIGNAL / 02

User correction · correction

The user overturns an earlier claim: "不对 / 其实是 / actually / I meant" — a correction means the old belief was wrong, and the new conclusion is worth keeping.

"No wait — it's pnpm, not npm"
SIGNAL / 03

Resolved failure streak · pitfall-resolved

Same-signature tool calls fail consecutively (≥2 by default) and then succeed — that success is a verified workaround, distilled into a pitfall entry. One-shot failures never enter.

tool error ×2 → ✓ → [pitfall]
Fallback

Two flush paths keep signals from being lost: compaction end (compaction/end) extracts from the shadowed raw events; session disposal (session/disposed) makes one final pass over the whole session (5-second cap, fire-and-forget, never blocking the event).

Admission

The extraction prompt is itself a gate: anything the repository already records, transient states and unverified assumptions, procedures never verified by a tool are excluded; preferences need an explicit ask or a recurring topic. The line protocol emits [anchors:…] and [project] tags, with projectName taken from the highest-precedence source.

Curation

Every 20 sessions, the curator picks the longest entries (≥400 characters) — at most 5 per batch — and has the extraction model rewrite them into concise one-liners. The store forgets, and it also distills.

WHY · WHY DESIGNED THIS WAY

Why collect loose and admit strict?

The collection layer deliberately widens the funnel and pushes conservatism into the extraction prompt: a missed signal is a white loss — the truth is gone for good; a false positive is nearly free — the next station's dedup and consolidation will cut it. Put the gate in the wrong place and the costs are asymmetric.

entries

soft cap 500 (entriesCap, configurable)

The main memory table. Writes serialize on the domain write chain; past the soft cap, eviction follows the use signal (pinned immune; lowest accessCount / lastRecalledAt first), and when everything is exempt the store may exceed the cap — healthy data is never hard-deleted.

audit

cap = 200 rows · monotonic seq

Every successful change appends: action, source (tool / review / flush / ui / janitor), content preview. Who wrote it and when is forever queryable.

suggestions

cap = 200 rows

The review mode's pending queue. A proposal is not a memory — not injected, not searchable, not decayed; it waits for a human verdict (station 07).

meta

new in v0.9

System metadata: the SQLite migration watermark (preventing a second migration), whole-store sweep progress and cooldown, consolidation-pipeline bookkeeping.

There is also cross-process single-writer detection: the storage backend assumes one writer per process — two DSH processes sharing a storage root would silently clobber each other. On every boot memory-store stamps an owner mark (pid + bootId) into the domain's global slot and re-reads it periodically: reading back a live stamp that isn't yours proves a concurrent publisher, reported immediately. It only detects, never locks; a dead pid or a cleanly-exited predecessor is not a live threat, so restarts don't false-positive.

WHY · WHY DESIGNED THIS WAY

Why is SQLite optional rather than the default?

host-medium rides the host storage domain — isomorphic with the other plugins, no extra files — and small write volumes work perfectly well on it. SQLite serves high-write scenarios (auto-extraction + sweeps + hit stamps), collapsing whole-file write amplification into one transaction per write. Migration happens exactly once and is one-way, and both sides fail loud — two coexisting backends would only produce silent divergence, a worse failure than slowness.

03

Grow: dedupe, consolidate, supersede

A new entry doesn't just pile into the store — it first confronts the memories already there.

Sweep

A whole-store sweep (opt-in, off by default): every 20 session creations, the top 20 pairs ranked by the use signal go through the verdict protocol again — built to catch synonymous rewrites sharing zero tokens; progress and cooldown (≥1 hour) persist in the meta table.

Hits

A usage-hit signal (opt-in, off by default): entries injected each round enter a per-session ledger; when the assistant's answer echoes an entry's tokens or anchors, hitCount / lastHitAt +1 — it only feeds sweep selection, never deletion.

WHY · WHY DESIGNED THIS WAY

Why does conflict directly supersede the old entry?

An overturned conclusion that keeps being injected as a "fact" is the memory store's most dangerous lie — the model would argue with present reality using expired information. Superseding is not deleting: the original text, the audit trail, and the supersededBy pointer all survive, the evidence chain stays complete — it just stops being treated as current truth.

04

Recall: dependency-free BM25

No vector store, no embedding model — a hand-rolled Okapi BM25 with CJK-aware tokenization and conservative Latin stemming.

Retrieval is two steps: structured filters first (scope / category / projectName), then BM25 scores the survivors — with document frequencies computed over the full corpus, so common words can't inflate inside a small candidate pool. The tokenizer splits Latin words and strips one conservative suffix to fold forms (uses→use, studies→study; class and basis are never damaged); for CJK it emits single-character unigrams plus adjacent bigrams — bigrams stop "记忆" from matching every entry containing "记", unigrams keep single-character queries alive. summary joins the index alongside content. Final order: relevance ↓ → pinned ↓ → importance (absent reads mid-range) ↓ → recency ↓.

score = Σ IDF(term) × tf·(k₁+1) / (tf + k₁·(1−b + b·|d|/avgdl))　　k₁ = 1.2, b = 0.75, non-negative IDF variant

Zero-hit fallback: a non-empty query with no lexical hit returns the most recent entries under the same filters, flagged fallback: true — in the tool return only; injection surfaces never fall back. The benchmark exports as @chenhw7/dsh-memory/benchmark, and the golden set carries CI floors: success@5 ≥ 0.85, MRR ≥ 0.75, P@1 ≥ 0.6, zh-slice success@5 ≥ 0.8.

WHY · WHY DESIGNED THIS WAY

Why no vector retrieval?

Zero dependency is a recorded engineering constraint: BM25 is explainable, free at runtime, and runs offline in tests; Chinese bigram tokenization restores word-level precision. The honest cost is stated on the table — no cross-lingual or paraphrase semantics; the golden set's synonym slice rides on summary indexing. When real workloads prove lexical isn't enough, evaluate the upgrade then — today, don't pay complexity for a hypothetical requirement.

05

Inject: frozen snapshots, budgets, progressive disclosure

How memory enters the context decides every token it saves the model.

Each session freezes a memory snapshot at creation and reuses it for the whole session — prefix unchanged, KV-cache fully warm. The only re-freeze is compaction (the prompt is rebuilt anyway), so memories learned mid-session slip in exactly there. The memory section sits at system-prompt order 90 (before tool guidance), with project-notes right behind at 91.

Optional step-level auto-recall takes the other road: on every agent step, a BM25 search keyed on the step's user text appends matching entries as a <recalled-memory> fenced user message — max 5 entries, queries at least 12 characters, fence ≤1200 chars with a token footer; the system prompt is untouched, the prefix cache unmoved. At load time, entries contradicted by newer facts carry conflict annotations (fresh / stale / conflicting, from a pure IDF-weighted detector), letting the model weigh old against new itself.

WHY · WHY DESIGNED THIS WAY

Why is index the default mode?

The existence index's size grows with category count, not entry count — standing cost stays bounded and budgetable (policy-only is a flat ≈344 tokens; full mode dual-budgets 5000 chars / 20 entries). The model sees what exists and pulls full text via memory_get on demand: progressive disclosure preserves both KV-prefix stability and the token budget.

WHY · WHY DESIGNED THIS WAY

Why two tiers of decay?

The project scope is bound to a repository: the repo moves on, the conventions change — expired project memories left in place only pollute retrieval, so they are hard-deleted when overdue. global / user are cross-project assets where a wrong deletion costs far more than retention — stamp instead of delete, and one recall overturns the stamp. Different stakes deserve different deaths.

07

Farewell: even forgetting has ceremony

Deletion is the heaviest operation in the system — so every step of it is gated.

FORGET · BATCH FORGETTING

The four locks on memory_forget

An explicit confirm: true double confirmation; batches over half the search cap are refused outright (runaway protection); pinned entries are skipped and reported; every removal is individually audited. Topic-level forgetting never sweeps away your pinned keepers.

RAW · THE BREAK-GLASS

Blocked content stays repairable

Scanner-rejected content never lands; content already stored that turns out problematic comes back through memory_get's raw: true for repair — and the break-glass read itself enters the audit. The original is always inspectable; silent deletion would only hide the attack.

Finally, the remote boundary: the memory console's 15 RPC methods are read-only by default — writes sit behind one deployment-level switch (remoteWritesEnabled). What is trusted is the transport fence (loopback / LAN / trusted hosts, owned by the host), not the storage face: a wider trust scope never silently grows into whole-store write access.

Frequency is the signal

Proposals observed repeatedly accumulate hits and float to the top; entries recalled repeatedly stay fresh. Usage traces are the most valuable metadata there is.

Stability over freshness

The snapshot freezes for the KV-cache for the whole session — better a one-beat delay than a wobbling prefix. Cache hits save far more than instant injection earns.

Memory is context, not instructions

Every injection surface declares it: the current user request, repository files, and tool output always outrank memory. On conflict, trust the present.

Every write is auditable

37 scanner rules, audit / suggestions rolling at 200 each, entries soft-capped at 500, the optional review queue — a memory system must be able to answer "who wrote this memory, when, and why".
