# Agent Note: Memory write-path rework — SQLite local backend and two-tier batch consolidation

Status: proposed

## Problem

The 2026-09-02 core-v0 judged report (`/tmp/eval-full-c2-20260902.json`, real model + judge, rubric v1, 32 scenarios / 114 questions) and the eval audit ([eval-audit-and-noisy-corpus](../../implemented/testing/2026-09-03-eval-audit-and-noisy-corpus.md)) expose three structural write-path defects:

1. **Duplicate writes of the same fact.** 10 planted facts were written 2–3 times among 52 stored entries. The weakest of the four dimension means is contentFidelity (0.892); mergeBehavior (1.382) is next, but it is the *least trustworthy* dimension to measure — the `writtenIds = after − before` accounting never routes merges/updates to the judge, so the dimension only measures "was a duplicate created" (audit zh.md:21).
2. **Contradicting writes without conflict annotation.** prog101 wrote an "npm only" entry contradicting the stored pnpm convention; both coexist with no deprecation marker (the "lexical detection of reworded corrections" gap in [conflict-resolution residual](../../implemented/architecture/2026-09-01-forget-selfcheck-conflict-residual.md) materialized on real corpus). The code reality goes further: the write path *structurally has no conflict channel* — the judge's verdict set is duplicate/update/new only, "merge" is lexical concatenation (`src/review/dedup.ts:107-115`), and cross-scope entries are never compared (`dedup.ts:77`), so a prog101-class contradiction is unreachable at any lexical threshold.
3. **Lost scope attribution.** prog112 names the ui-kit repo explicitly, yet entries lack project attribution and surface under the wrong repo context — `ParsedMemory` (`src/review/extract.ts:174-183`) has no projectName field, so project attribution can only be cwd-inferred (`extract.ts:567,599`).

All three trace to one design error: the write path gates a *semantic* decision (same fact? contradiction?) behind `findDuplicate`'s IDF-weighted lexical overlap, which cannot measure semantics — reworded true duplicates score in the same band as 「上海/海南」-class distractors, so the LLM judge never fires.

The storage medium compounds the problem. The host storage-json republishes the whole unit file with fsync on every write: the integration suite once blew a 5s CI budget at 205 adds ≈ 415 fsync'd publishes, a symptom since fixed by seeding the medium ([audit-cap-test-seeds-medium](../../implemented/testing/2026-09-03-audit-cap-test-seeds-medium.md), ~415 → ~7) — so it is no longer an incident, only a measurable proxy for write amplification in real usage. Cross-process safety is hand-rolled detection over the host's last-writer-wins semantics ([cross-process-detect](../../implemented/architecture/2026-09-01-cross-process-detect-owner-stamp.md)). The persistent state consolidation needs (watermark, cooldown, deprecation markers) has no natural home in a single-file medium beyond adding another table. The roadmap features (usage-driven forgetting, consolidation baselines, anchor indexes) are relational-query shaped — at ≤500 entries in-memory filtering is cheap; what is actually missing is write atomicity granularity and a place for that state. The `DomainMemoryStore` scale-selfcheck comment already reserves the slot for the "SQLite backing" migration (`src/store/index.ts:393-418`).

Reference: OpenAI Codex CLI memories (`~/codex/codex-rs/memories`, deep-read 2026-09-04) answers the same problem with **zero semantic dedup at write time** (thread_id primary-key upsert) and **all merge/conflict delegated to a periodic, whole-corpus LLM consolidation** (cooldown-gated, usage-top-N selection), on a separate SQLite state DB, with usage counts driving selection and forgetting. The load-bearing lesson is the pairing: a *dumb* write is only safe because a *periodic full-context sweep* catches everything the write did not.

## Proposal

Four phases, ordered "fix the defects first, plumbing second": Phases 1–2 land on the existing host-medium backend (zero-migration field/table evolution), Phase 3's SQLite is an independent plumbing release, Phase 4 is scoped only. Each phase is independently shippable and revertible and lands as its own commit + Agent Note; mechanical acceptance reuses the eval infrastructure. The decisions below are final as of this amendment; if implementation forces a contradiction, amend this note and mark the amendment. Execution-level steps (files, symbols, commit slicing) live in the sibling note [write-path-rework-implementation-plan](./2026-09-04-write-path-rework-implementation-plan.md).

### Phase 1: anchors + two-tier batch consolidation (the dedup/conflict fix, on the existing backend)

- Extraction schema increment (same LLM call, zero extra round trips): `ParsedMemory` gains `anchors: string[]` and `projectName?: string`; the line protocol follows the `[summary:…]` tag precedent with new `[anchors:…]` / `[project:…]` tags. The extraction prompt hard-requires a repo name/path in conversation to enter anchors and fill `projectName`; the NO-OP gate stays (low-signal rounds may return empty). `storeMemories` attributes project scope from parsed.projectName first, cwd-inference as fallback — this fixes prog112.
- Entry model and state table (all zero-migration, per HOST_CONTRACT §1's optional-field/absent-table semantics): `MemoryEntry` gains optional `anchors`, `status: 'active' | 'superseded'` (absent reads as active), `supersededBy`, with the zod mirror updated in step; the domain gains a fourth table `meta` (absent tables initialize as empty maps) holding consolidation progress lastRun/cooldown.
- **Two-tier consolidation — anchors are a prefilter, never the completeness guarantee:**
  - **Per-round tier (cheap):** consolidation candidates = lexical weighted overlap ∨ shared low-frequency anchor (df ≤ 2), bucketed same-scope / cross-scope. Cross-scope pairs are no longer structurally excluded by `dedup.ts:77`'s same-scope contract; they route to conflict/scope repair instead (environment observation ≠ convention; different scopes do not merge by default). The candidate selector is new code over the bm25 primitives and does not change `findDuplicate`'s contract. One structured LLM call (following the repo-wide line-protocol discipline: the judge's one word, the curator's `<id>:` lines) returns per candidate `{action: merge | update | conflict | new, targetEntryId?, content?}`, under anti-over-merge rules.
  - **Periodic full-corpus tier (the backstop that makes the dumb write safe):** once on startup plus the curator's per-N-sessions gating, re-run consolidation over the usage-top-N of the whole corpus (codex `get_phase2_input_selection` semantics: access_count DESC, COALESCE(last_recalled_at, updated_at) DESC, filtered by the decay window). This tier sees reworded duplicate pairs that share no hard token and pre-anchor legacy duplicates — exactly the pairs the per-round lexical/anchor prefilter structurally cannot reach. **A lexical or anchor prefilter alone re-creates the Problem's design error; this sweep is the channel that actually measures semantics.**
- `conflict` → old entry `status='superseded'` + `supersededBy` + a visible deprecation annotation (credited by rubric v2), new fact lands as a new entry; `merge`/`update` keep the existing `mergeContent` semantics. Unparseable consolidation output fails closed to `new` (never mis-merge: a false duplicate swallows a fact, while a false new leaves redundancy the periodic tier can salvage — the opposite direction from the judge's fail-closed-duplicate; the rationale lands in the code docstring). Retrieval surfaces (standing-section assembly, auto-recall, search) filter superseded entries, following the staleSince filter precedent; the tool surface (memory_list/memory_get) keeps them visible with the annotation.
- The per-pair `judgeDuplicate` stays for **one release** behind a new Config `consolidation: 'two-tier' | 'legacy-judge'` (default two-tier) as a kill switch, then is deleted; the removal is recorded by updating this note when it ships.

### Phase 2: usage feedback and forgetting

- **Hit signal = "token ∩ answer" weighted**: new optional `hitCount` / `lastHitAt` (zero-migration); an entry accrues only when the answered turn's text overlaps its tokens/anchors (IDF-weighted above a calibrated threshold), so an injected-but-ignored entry earns nothing. Plug-in points: the auto-recall pre-step records this round's injected ids (`src/context/index.ts:387-412`), the standing-section snapshot (`:337-364`), and an `assistant/message` session-event listener (precedent at `src/review/index.ts:296`; text extraction reuses the accumulator's messageText logic) triggers the intersection and the write-back. "+1 on injection" is rejected — it makes usage a proxy for index size, not usefulness.
- **Existing `accessCount`/`lastRecalledAt` semantics unchanged**: the recall/surface count keeps feeding `trimEntries` eviction order (`src/store/index.ts:819-839`) and the decay judgment; redefining them as "count only on answer overlap" is rejected (see Alternatives). The periodic consolidation's top-N selection switches to a hit-aware ordering (the combination rule is calibrated during implementation and recorded in this note).
- **Forgetting stays a single knob.** No new `maxUnusedDays` is added; the existing `decayDays` janitor (default 30, `0` = off) remains the only forgetting control, and `entriesCap` still backstops. Codex's `max_unused_days` is reused **only** as the selection filter for the periodic top-N input, never as a second deleter. Known bounded bias: an entry the model used without echoing its tokens in the answer gets under-counted — under-counting only affects consolidation selection order, never deletion (decay reads recall time), see Risks.

### Phase 3: SQLite local storage backend (independent plumbing, wholesale revertible)

- **Motivation corrected (from the first draft): this phase fixes none of the defects named in Problem** — Phase 1 fixes those. It buys four pieces of architectural hygiene: write atomicity granularity (single-record writes vs whole-file republish + fsync — in real usage every per-round consolidation write amplifies into a full-file write), consolidation state and deprecation markers settling in the same transaction as the records they describe, moving memory data off the host's last-writer-wins single-file medium, and leaving room for the roadmap's relational queries. Two first-draft motivations were rejected in review: the 5s CI budget blowup is already dissolved by medium seeding (see Problem), and the "relational query shape" is microseconds of in-memory filtering at ≤500 entries — circumstantial evidence, not justification.
- Add `SqliteMemoryStore extends MemoryStore` (`src/index.ts:63`) on `node:sqlite`'s `DatabaseSync`, pinning the minimal API surface (open + prepare + exec). DB file `$DSH_HOME/storages/memory.db`, WAL mode + busy_timeout (multi-process concurrent-write semantics pinned by acceptance). **Precedent corrected:** the notesDir precedent does not hold (notesDir has been ignored since 0.6 and is being dismantled, `src/notes/settings.ts:32`) — `memory.db` is a plugin-named new file inside the host's storages directory; local-medium ownership, the WAL sidecars (`-wal`/`-shm`), and uninstall semantics are recorded together in HOST_CONTRACT and TECH_DESIGN (§6.3/§10.4).
- Tables: `entries` (all MemoryEntry fields + the Phase 1/2 additions), `audit`, `suggestions` (migrated with their domain-table shapes), `meta` (schemaVersion, consolidation lastRun/cooldown — consolidation state migrates with the data).
- Config gains `storage: 'host-medium' | 'sqlite'` via cordis.patch.yml + the settings card; misconfiguration fails loud. **This release ships `host-medium` as the default with `sqlite` opt-in; the default flips to `sqlite` in the next release, gated on this phase's acceptance passing.**
- One-time migration: SQLite backend opens with an empty DB and a non-empty host medium → import and write the `migratedToSqlite` marker into the medium's **meta table** (not the owner-stamp global slot — the global slot's schema belongs to CrossProcessGuard); both non-empty → fail loud.
- Cross-process: the host-medium backend keeps the full CrossProcessGuard. **The mixed-version marker ships:** a process starting on host-medium that finds `migratedToSqlite` in the medium meta table fails loud (direct-medium-read precedent: `src/store/cross-process.ts:69-117`), so an old process can never silently write `memory.json` while a new one owns `memory.db`. The SQLite side relies on WAL + busy_timeout single-writer semantics, pinned by concurrent-writer tests.
- BM25 kernel and CJK tokenizer untouched (recorded zero-dependency exceptions); the retrieval plane does not change. entries+audit settle atomically in one transaction. The host storage layer is itself backend-agnostic (the descriptor comments the unit name as "file-name / SQL-identifier segment", a slot already reserved for SQL backends) — why we do not attach along that seam is recorded in Alternatives.
- **Prerequisite (acceptance gate):** `node:sqlite` has needed no `--experimental-sqlite` flag since Node 22.13.0 (verified on 22.22.2: open/prepare/exec/FTS5 all work), and on 22.x–24.x the first use emits one `ExperimentalWarning` to stderr (from 25.7.0 it is a release candidate and emits nothing). The premise "the host pins `engines` floor `^22.19.0 || >=24.0.0`" is unverifiable inside this repository (this package.json has no engines field) — record it into HOST_CONTRACT before work starts, re-validate the better-sqlite3 rejection against it, and acceptance includes "the warning does not break host stderr assertions".

### Phase 4 (scoped only): curated index view

Standing injection reads the deduplicated index view produced by consolidation, raw entries as payload (codex's dirty-store/curated-summary two layers). Precondition: Phases 1–3 stable + a v2 A/B baseline on record.

## Alternatives considered

- **Copy codex wholesale (sub-agent consolidation + git-repository memory folder + citation protocol)** — no. The consolidation sub-agent (medium reasoning + file tools) does not match our per-round cadence → downscaled to a structured call; change tracking uses the consolidation watermark, not git diff; the citation protocol would touch the host → "token ∩ answer" comes first. Codex's *periodic full-corpus sweep* is adopted (Phase 1); its *file-based memory + agent-grep recall* is not — that would discard our structured scope/category/BM25 retrieval, a genuine advantage codex lacks.
- **Anchors as the sole consolidation trigger (this plan's first draft)** — no. Anchors are still a lexical signal: a reworded duplicate pair with no shared hard token never triggers, re-creating the exact "semantic decision gated behind a non-semantic metric" error the Problem names. The periodic full-corpus sweep is the completeness guarantee; anchors survive only as the per-round prefilter.
- **Triples / entity graph / canonical field** — no deterministic consumer; grouping and conflict candidates are covered by anchors + the full sweep, and the merge decision belongs to the consolidation judge reading full text. Canonicalization is itself unstable and LLM extraction variance would become a new dedup noise source.
- **Keep tuning the lexical metric (threshold/weights/Jaccard)** — no. Lexical similarity has a structural ceiling for "same fact, reworded"; moving the threshold only moves the error distribution (reworded corrections ≈0.02 vs distractors ≈0.06, see the calibration in the conflict-resolution residual note).
- **better-sqlite3** — no (premise to be recorded). The argument "the host engines floor guarantees `node:sqlite`" depends on the host composition pinning ≥22.13, a premise absent from this repository and to be recorded into HOST_CONTRACT first; once it holds, a native module loaded into the host process risks an ABI/install hard-failure that kills the whole plugin. `node:sqlite`'s experimental API-drift risk is bounded by the minimal API surface behind `SqliteMemoryStore`. This is a plugin-distribution decision, not zero-dependency dogma. (Verified flag-free on 22.22.2.)
- **SQLite FTS5 (replacing or paralleling BM25)** — no, and the listed behaviors were reproduced live on `node:sqlite`: the default `unicode61` tokenizer treats a contiguous CJK run as one token (stored 「上海」 is not found by querying 「上」 — 0 hits); `trigram` requires ≥3-char queries and misses the most common 2-char Chinese words (「记忆」 → 0 hits); and node:sqlite exposes no FTS5 custom-tokenizer hook (a C API reachable only by a compiled extension via `loadExtension` — a heavier native dependency than better-sqlite3). At ≤500 short entries the in-memory BM25 scan is microseconds, so FTS5's disk-backed index gives no performance benefit, and a parallel index would add a shadow index plus two ranking systems to reconcile. The existing unigram+bigram tokenizer already solves CJK.
- **Moving entries into the host medium in a new format** — no. storage-json is a host peer contract; unilaterally changing the format breaks compatibility. SQLite enters as a plugin-owned local backend behind the `MemoryStore` abstraction. (One description corrected: remote/ is not an alternative storage source but an RPC adapter over the same memory service; it rides the service abstraction, so a backend swap is transparent to it and the "unaffected" conclusion stands.)
- **SQLite first (this proposal's first-draft ordering)** — no. The original order placed a full plumbing release that fixes none of the named defects ahead of the repair, and neither support holds: the CI fsync symptom was dissolved by medium seeding, and "avoid two migrations" does not — the JSON side evolves by zero-migration optional fields and an absent-means-empty table, the consolidation state rides the meta table into SQLite with the single import, and the migration count is constant at one. Consolidation first repairs the 9/2 report's defects at minimal risk; SQLite afterwards keeps its full value as an independent release.
- **Registering a SQLite StorageBackend on the host storage hub** — no. The host storage layer is indeed backend-agnostic (see Phase 3), but memory's composition row belongs to dsh-web-app, not this bundle (TECH_DESIGN §10.3) — attaching along that seam means coordinating a host change; the `MemoryStore` abstraction seam is plugin-owned with zero host change. If the host later ships an official SQLite backend, `SqliteMemoryStore` can be replaced by a bridge.
- **Redefining `accessCount` to "count only on answer overlap"** — no. The field is already consumed by `trimEntries` eviction order and the decay judgment; silently switching its semantics changes the meaning of standing data and ranking. New `hitCount`/`lastHitAt` fields are zero-migration and semantically independent; the combined ranking is calibrated in Phase 2.

## Acceptance criteria

- **Phase 1:** the 10 duplicate pairs from the 9/2 report → consolidation triggered 10/10; a fixture proves the **periodic full-corpus tier** merges a reworded-duplicate pair sharing **no** anchor; `tests/dedup.spec.ts` calibration pairs with zero regression; replaying prog101/112/201/303: stored entries 52 → ≈40, duplicate fact pairs 10 → 0, unannotated contradictions → 0, prog112 projectName in place; `status='superseded'` filtering on injection surfaces and annotated visibility on the tool surface each pinned by a test; bidirectional compatibility pinned (an old medium without the new fields/meta table opens zero-migration; a new medium carrying new fields and an unknown table survives a read-then-write through the old code path without losing the table); the kill switch (legacy-judge) behavior covered by a test; batch-consolidation vitest on fake-LLM routing (the `tests/eval-fakellm.spec.ts` precedent, real-model runs keep the env-gated discipline).
- **Phase 2:** hitCount readable in eval scenarios and accrued only on answer overlap (two opposing fixtures pin it: "injected but ignored earns nothing" and "answer echo earns +1"); `decayDays` remains the sole forgetting knob (no `maxUnusedDays`); the forgetting queue never swallows entries needed by negative questions; same-build A/B EQUAL on the deterministic layer.
- **Phase 3:** the host engines floor recorded into HOST_CONTRACT first; existing store/review specs parameterized over both backends all green; the composition reopen case covers SQLite; same-build "host-medium vs sqlite" eval A/B with per-scenario EQUAL on the deterministic layer; the CI write-amplification case re-baselined under SQLite with the seeding trick retired; the mixed-version fail-loud marker and meta-table survival covered by tests; WAL busy_timeout multi-writer behavior covered by a test; the `ExperimentalWarning` confirmed harmless to host stderr; HOST_CONTRACT gains local-medium ownership + a §10 checklist item; TECH_DESIGN §6.3/§10.4 gains memory.db, the WAL sidecars, and uninstall semantics.
- **Throughout:** no v1↔v2 rubric score comparison; acceptance uses mechanically countable metrics + a fresh v2 baseline; the v2 judged A/B rerun (once the gateway recovers) is the behavioral acceptance gate.

## Risks

- Over-merging by the consolidation judge → anti-over-merge prompt rules + fixtures (environment observation vs convention); conflict is conservative (annotation over deletion); parse failures fail closed to `new` — redundancy over swallowed facts.
- LLM cost/latency of consolidation → per-round input is anchor-bounded; the periodic full sweep is bounded by its per-N-sessions/cooldown gate + top-N cap + usage-rank selection; a config kill-switch reverts to per-round-only or legacy-judge.
- The periodic sweep stacking on the existing curator's triggers → both reuse the same per-N-sessions gating and ledger; frequencies are exposed by the same Config group; failures all accounted via `reportFailure`.
- Usage under-counting (the model used a fact without echoing its tokens) → bounded: the under-count only feeds consolidation selection; decay/janitor never read hitCount; if the hitCount readout in the eval mechanical layer shows selection bias, retune by weight config.
- `node:sqlite` is experimental; a host Node upgrade may drift the API → minimal API surface behind `SqliteMemoryStore`, full spec coverage, a HOST_CONTRACT §10 checklist item. Named fallback if it becomes unusable: better-sqlite3 behind the same `MemoryStore` seam, or revert to `host-medium`.
- Dual sources of truth (medium retaining old data once sqlite is enabled) → one-way migration + the Phase-3 fail-loud mixed-version marker; ambiguity fails loud.
- Phase 4 changes the injection plane → scoped only after Phases 1–3 are stable; eval's standingHit/noiseRatio mechanical layer measures regressions directly.
