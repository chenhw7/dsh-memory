# Agent Note: The bundle moves to the DSH 0.2 host contract

Status: implemented

English | [中文](2026-11-25-dsh-0.2-per-entry-settings-and-client-page.zh.md)

## Problem

DSH 0.2 replaced the host surfaces this bundle was built on, so the 0.9.x package could not load at all:

- **Settings lost their runtime read.** `ctx.settings.installSection(...)` and `ctx.settings.get(ns)` are gone; `SettingsForms` is now a form/wire surface only (`describe`/`update`/`replace`/`mutate`). Each profile entry instead exports its own `Config`, receives it in `apply(ctx, config)`, and is re-applied when a card commits a change.
- **The client settings transport was replaced.** `ctx.settingsScope.bind({ namespace })` and `SettingsScopeSnapshot` no longer exist; the Plugins page lost the namespace-keyed `settings.plugin.item` card slot and gained `plugins.bundle.config` / `plugins.row.config`, fed by `ctx.configForms.get(entryId)`.
- **Smaller vocabulary breaks.** `MessageSourceMap` lost the catch-all `plugin` kind (each producer declares its own), tool results stopped being content blocks (`tool/result.data.message` is a tool-role message), `session.events` stopped existing (synchronous log reads are deprecated), `sessionProjections.register` became awaitable and returns the supported read handle, `dsh-invariants` was removed as a package, and `ctx.tools.execute` now requires a mounted tool executor.
- **Version gate.** 0.2 enforces `engines.dsh` / peer ranges at install time, so a `^0.1.2-alpha.2` declaration refuses to install rather than failing later at runtime.

The interesting part is not the mechanical port but the two decisions the port forced: where the shared knobs live once no plugin can read another's settings, and where the configuration UI lives once the namespace-keyed card slot is gone.

## Decision

**One entry per settings surface, and cross-entry knobs travel through the owning service.** The bundle rows were renamed so that the row id *is* the settings namespace the host addresses: `memory` (store), `memory-tools`, `memory-review`, `memory-notes`, `memory-identity`, `memory-autorecall` (context), `memory-remote`, plus the unchanged scanner no-op `memory-root`.

| Entry | `Config` | Publishes |
|---|---|---|
| `memory` | storage backend, `entriesCap`, `crossProcessProbeMs`, and the injection/recall slice (`memoryMode`, `memoryPolicyCustomText`, `memoryCharLimit`, `memoryDigestCharLimit`, `memoryMaxEntries`, `maxSearchResults`, `decayDays`) | `ctx.memory.settings()` |
| `memory-autorecall` | `autoRecallEnabled`, `autoRecallLimit`, `autoRecallMinChars`, `hitSignalEnabled`, `hitSignalThreshold` | — |
| `memory-notes` | `notesEnabled`, the two budgets, `notesMaxEntriesPerFile` | `ctx.projectNotes.settings()` |
| `memory-identity` | `identityEnabled`, `soulCharLimit`, `userCharLimit`, `identitySeedDir` | `ctx.identity.settings()` |
| `memory-review` | the review/extraction/curator/sweep slice, incl. `confirmBeforeWrite` | `ctx.memoryReview.settings()` (new, minimal face) |
| `memory-tools` | `scannerAllowlist` + the composition fallback for the search cap | — (reads the four services) |

The injection budgets sit on the store entry because `ctx.memory` is the one memory service every sibling already resolves; `confirmBeforeWrite` stays on the review entry because the review page owns that field and the tool is merely its enforcer. `MemoryStore`, `ProjectNotesService` and `IdentityService` each gained a `settings()` member, so the value a card writes is read back from the plugin that declared it.

**The configuration UI is one bundle page, not five cards.** `src/client/index.ts` registers a single contribution into `plugins.bundle.config` keyed by `@chenhw7/dsh-memory`, gated by `ctx.configForms.whileServed([...entry ids])`; the page renders five collapsible sections (`MemoryPluginCard.tsx` → `MemorySection`, `NamespaceCard.tsx` → `NamespaceSection`) and hands each one that entry's `ConfigForm`. Saving submits the whole staged draft as one `mutate(ops, revision)` — one revision fence, one Host validation, one recovery read — instead of one write per changed field.

Three follow-on decisions inside the port:

- **Message sources are declared, not borrowed.** `src/sources.ts` augments `MessageSourceMap` with `memory-context` and `memory-review`. The step-tail message uses `form: 'snapshot'` with named `sections` (`memory-digest`, `recalled-memory`) because a later fence supersedes the previous round's set; the extraction prompts carry no form, since they never join a session surface.
- **The compaction flush keeps its own log.** Because `session.events` is gone, `memory-review` maintains a bounded per-session map (seq→text, cap 500) plus `compactionId`→`shadowedSeqs`, fed by the global `session/event` listener it already runs. No deprecated synchronous read is used.
- **Frozen prompt snapshots rebuild lazily.** A settings change restarts the entry's fiber, which clears the per-session `WeakMap`s. The context plugin therefore freezes on first touch (`snapshotOf`) instead of only on `session/created`, so a live session's memory/notes/identity sections do not blank out until the next session starts.

## Alternatives considered

**Keep a shared "memory settings" namespace and read it cross-plugin.** Impossible: 0.2 has no cross-entry settings read at all, and re-deriving one from `ctx.settings.describe()` (the UI-facing, redacted, revision-tagged view) would couple config reads to a wire API built for forms.

**Keep one giant `Config` on the context entry** (the 0.1.x composition shape) and have every other row receive its slice through a service the context plugin publishes. Rejected: it moves the store's backend knobs into the prompt-injection plugin, and it leaves four of the five settings surfaces without an owning entry, so the settings page could not address them.

**Register one `plugins.row.config` page per row** instead of one bundle page. This is the host's per-row shape and would look closer to the old four cards, but the row page header comes from `readPluginMeta(specifier)` — `<specifier>/locale/<lang>.json`'s `meta.title` — so each subpath would need its own locale resource and export entry, and five tiny pages would each repeat the same save/discard chrome. The bundle page keeps one locale dictionary and one page to maintain.

**Serve the UI from `plugins.item`.** That slot is documented as occupied by the official settings pages, and its copy explicitly routes a bundle's own configuration to `plugins.bundle.config` / `plugins.row.config`.

**Keep the digest flag across a restart by scanning the session for a previous digest message.** Rejected as a per-step cost on long sessions for a rare event; the trade-off is recorded under Consequences instead.

**Keep 0.1.x compatibility behind a dual-path adapter.** Rejected: the settings model, the message-source vocabulary and the client transport all changed shape, so the adapter would have had to reimplement two host contracts and keep tests for both — the maintainer chose a clean 0.2-only line (a 0.10.0 breaking release) with 0.9.x left for 0.1.x hosts.

## Consequences

- **Renaming a row renames its settings entry.** User overrides stored under the old ids (`memory-store`, `tool-memory`, `memory-context`) stop applying on upgrade. The row ids are now a durable contract, documented in `cordis.patch.yml`.
- **The `./invariant` subpath is gone** (`dsh-invariants` no longer exists). Consumers importing it must drop the import.
- **A settings change can re-emit the one-time digest.** The `digestSent` flag lives in the fiber's `WeakMap`, so the restart loses it and the next step may re-send the inventory once. Accepted: settings changes are rare, the message rides the step tail (never the cached prefix), and making the flag durable would need a per-session scan on every step.
- **`zod` is pinned to the host's exact version (4.6.6).** `domainTable`'s schema types must be the same instance the storage-domain package sees; a caret range resolves to a newer patch and produces a second copy, which fails the type check on `domainTable(...)`. Bumping devDeps means re-pinning it.
- **Tool execution needs an executor in test compositions.** `@deepseek-ai/dsh-tool-executor-native` became a devDependency so the tool specs mount it; without one, `ctx.tools.execute` fails with `ToolExecutorUnavailableError`.
- **The GUI regression risk is real but bounded:** the page's fields, drafts and revision-fenced save are covered only by the client type gate and manual use — the previous per-card layout had no browser test either.
- **Bought:** the bundle loads and stays installable on 0.2.x, the config surface is one page with one dictionary, the settings slices live with the plugins that own them, and no deprecated host API remains on any read path (no `session.events`, no `installSection`, no `settingsScope`).

## Testing

`npm run build` (host `tsc` + client gate + esbuild bundle) and `npm run test` (vitest, including the integration composition specs) gate the change; the tool specs mount the native executor, and the composition specs exercise the per-entry configs through `apply`.
