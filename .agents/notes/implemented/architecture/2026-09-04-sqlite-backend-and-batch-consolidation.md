## Problem

The 2026-09-02 core-v0 judged report (`/tmp/eval-full-c2-20260902.json`, real model + judge, rubric v1, 32 scenarios / 114 questions) and the eval audit ([eval-audit-and-noisy-corpus](../testing/2026-09-03-eval-audit-and-noisy-corpus.md)) exposed three structural write-path defects:

1. **Duplicate writes of the same fact.** 10 planted facts were written 2–3 times among 52 stored entries. The weakest of the four dimension means is contentFidelity (0.892); mergeBehavior (1.382) is next, but it is the *least trustworthy* dimension to measure — the `writtenIds = after − before` accounting never routes merges/updates to the judge, so the dimension only measures "was a duplicate created" (audit zh.md:21).
2. **Contradicting writes without conflict annotation.** prog101 wrote an "npm only" entry contradicting the stored pnpm convention; both coexist with no deprecation marker (the "lexical detection of reworded corrections" gap in [conflict-resolution residual](2026-09-01-forget-selfcheck-conflict-residual.md) materialized on real corpus). The code reality went further: the write path *structurally had no conflict channel* — the judge's verdict set was duplicate/update/new only, "merge" was lexical concatenation (`src/review/dedup.ts` `mergeContent`), and cross-scope entries were never compared (`findDuplicate`'s same-scope contract), so a prog101-class contradiction was unreachable at any lexical threshold.
3. **Lost scope attribution.** prog112 names the ui-kit repo explicitly, yet entries lacked project attribution and surfaced under the wrong repo context — `ParsedMemory` had no projectName field, so project attribution could only be cwd-inferred.

All three trace to one design error: the write path gated a *semantic* decision (same fact? contradiction?) behind `findDuplicate`'s IDF-weighted lexical overlap, which cannot measure semantics — reworded true duplicates score in the same band as distractor pairs, so the LLM judge never fires.

The storage medium compounded the problem. The host storage-json republishes the whole unit file with fsync on every write: the integration suite once blew a 5s CI budget at 205 adds ≈ 415 fsync'd publishes, a symptom since fixed by seeding the medium ([audit-cap-test-seeds-medium](../testing/2026-09-03-audit-cap-test-seeds-medium.md), ~415 → ~7) — so it was no longer an incident, only a measurable proxy for write amplification in real usage. Cross-process safety was hand-rolled detection over the host's last-writer-wins semantics ([cross-process-detect](2026-09-01-cross-process-detect-owner-stamp.md)). The persistent state consolidation needs (progress bits, cooldown, deprecation markers) had no natural home in a single-file medium beyond adding another table. The `DomainMemoryStore` scale-selfcheck comment already reserved the slot for the "SQLite backing" migration.

Reference: OpenAI Codex CLI memories (`~/codex/codex-rs/memories`, deep-read 2026-09-04) answers the same problem with **zero semantic dedup at write time** (thread_id primary-key upsert) and **all merge/conflict delegated to a periodic, whole-corpus LLM consolidation** (cooldown-gated, usage-top-N selection), on a separate SQLite state DB, with usage counts driving selection and forgetting. The load-bearing lesson is the pairing: a *dumb* write is only safe because a *periodic full-context sweep* catches everything the write did not.

## Decision

Three phases shipped, ordered "fix the defects first, plumbing second"; each landed as its own commit sequence, independently revertible. Phase 4 (curated index view) remains scoped-only until phases 1–3 are stable and a v2 A/B baseline is on record.

### Phase 1 (shipped): anchors + two-tier batch consolidation

- **Extraction schema** (`src/review/extract.ts`): `ParsedMemory` carries `anchors: string[]` and optional `projectName`; the line protocol gained the trailing `[anchors:…]` / `[project:…]` tags, parsed right-to-left after the category/summary tags before the scanContent admission gate. The extraction prompts hard-require hard tokens (numbers, identifiers, tool names, repo names/paths) in anchors and a `[project: …]` tag when the conversation names a repo/project path; the NO-OP gate is unchanged. `storeMemories`/`suggestMemories` attribute project scope from the parsed tag first, cwd-inference as fallback.
- **Entry model** (`src/types.ts`, `src/store/index.ts`): `MemoryEntry` gained optional `anchors`, `status: 'active' | 'superseded'` (absent reads as active; supersession is terminal), and `supersededBy`; the zod mirror stays fully optional (zero-migration). The domain gained the fourth `meta` table (`MemoryMetaRecord`, a loose-carrier record keyed by subsystem prefix) exposed via `getMeta`/`setMeta`.
- **Per-round consolidation tier** (`src/review/consolidate.ts`): a lexical/anchor selector (`selectConsolidationCandidates`, built on the bm25 primitives; weighted overlap > 0.2 ∨ a shared anchor with df ≤ 2) proposes new-vs-stored candidate pairs, bucketed same-scope/cross-scope, capped at 20 pairs per call. When any candidate exists, ONE consolidation LLM call judges them over the line protocol `<candidateId> <action> [targetEntryId] [content]` (action ∈ merge/update/conflict/new) under anti-over-merge rules (environment observation ≠ convention; cross-scope defaults to new/conflict). Dirty or unparsable lines fail closed to `new` — the opposite of the judge's fail-closed-duplicate; the rationale lives in the module docstring. `conflict` flips the old entry through the `supersedeEntry` seam (status + `supersededBy` + the pinned `[superseded → <id>]` content annotation, audited) and stores the fresh fact; `merge`/`update` keep the `mergeContent`/`update` write shapes; every failure books as `consolidate-*`. With no candidates the batch writes directly with zero consolidation calls.
- **Periodic whole-corpus tier** (`src/review/sweep.ts`): on the first session creation after apply plus every `sweepEveryNSessions`-th creation, `rankForSweep` selects up to `sweepTopN` active entries by `hitCount` DESC → `accessCount` DESC → last-use DESC, `selectSweepPairs` proposes existing-vs-existing pairs on the shared lexical signal alone (anchors add nothing on an already-usage-ranked set), and at most one call judges them over the `p<N>` protocol. A dropped verdict fail-closes to inaction — nothing new exists to land. Progress persists in the meta table (`consolidation:lastRun`, ≥1 h between passes); `sweepEnabled` defaults to `false` (opt-in this release).
- **Superseded visibility:** the standing snapshot, the existence index, auto-recall, and `search` all filter `status === 'superseded'`; `memory_list`/`memory_get`/`memory_search` keep them visible with the content annotation and a structured `superseded: <id>` field.
- **Kill switch:** the review Config `consolidation: 'two-tier' | 'legacy-judge'` (default two-tier) keeps the original per-pair `judgeDuplicate` flow for one release; `dedup.ts` itself is untouched and its calibration tests still pin the legacy path.

### Phase 2 (shipped): usage feedback (hitCount)

- **The hit signal measures "did the answer use it":** `MemoryEntry` gained optional `hitCount`/`lastHitAt` (zero-migration). memory-context records the round's injected entries into a per-session ledger (the standing snapshot's set; the auto-recall fence's hits replace it for its round); on the round's `assistant/message`, `computeHits` weighs the answer's IDF-weighted coverage of each entry's tokens (content + summary + anchors) — an entry restated at or above `hitSignalThreshold` (default **0.25**; measured calibration bands: genuine restatement 0.5–0.7, incidental mention 0.05–0.12, unrelated ≈0) books one hit through the store's `markHits` (atomic read-modify-write, audited, `updatedAt` untouched, one hit per entry per batch). One answer consumes the ledger. `hitSignalEnabled` defaults to `false`.
- **`accessCount`/`lastRecalledAt` semantics unchanged** — recall/surface counting still feeds `trimEntries` eviction and the decay judgment; `hitCount` only reorders the periodic sweep's selection. **No `maxUnusedDays` was added** — `decayDays` (default 30, `0` = off) remains the only forgetting knob, and `entriesCap` still backstops.

### Phase 3 (shipped): SQLite local storage backend

- **`SqliteMemoryStore`** (`src/store/sqlite.ts`) over `node:sqlite`'s `DatabaseSync`, owning `$DSH_HOME/storages/memory.db` (WAL mode, `busy_timeout` 5 s; the `-wal`/`-shm` sidecars are part of the same unit). The API surface is pinned to open/prepare/exec; booleans bind as 0/1, objects/arrays as JSON strings, NULL = absent (the zero-migration read side). Tables: `entries` (`id` PRIMARY KEY, MemoryEntry columns), `audit`, `suggestions`, `meta`. Reads serve rows per call with the same synchronous semantics; writes are one statement per record with entries + audit in one transaction — no whole-file republish. Search re-uses the full-corpus BM25 df discipline; `supersedeEntry`/`markHits`/janitor/trim mirror the domain store's semantics; `close()` releases the connection.
- **The host engines floor** `^22.19.0 || >=24.0.0` (verified against the harness checkout's package.json) underwrites `node:sqlite` availability (flag-free since 22.13; an `ExperimentalWarning` hits stderr on 22.x–24.x); it is recorded in HOST_CONTRACT §11 together with the local-medium ownership, the WAL sidecar semantics, and the §10 checklist item. This package carries no `engines` field by design.
- **Backend selection:** the `memory-store` row's `StoreConfig` gained `storage: 'host-medium' | 'sqlite'` (default `host-medium` this release; the flip to `sqlite` next release is gated on the eval A/B re-baseline). The composition switches on it; the `remote/` RPC layer rides the service abstraction unchanged.
- **One-time migration:** a sqlite boot over a non-empty, unmarked medium imports entries + audit + suggestions verbatim in one transaction and stamps the medium's meta table with `medium:migratedToSqlite`; either backend booting over a medium with data AND the marker fails loud — two live sources of truth would diverge. CrossProcessGuard remains host-medium-only.

### Phase 4 (scoped only): curated index view

Standing injection reads the deduplicated index view produced by consolidation, raw entries as payload (codex's dirty-store/curated-summary two layers). Precondition: phases 1–3 stable + a v2 A/B baseline on record.

## Alternatives considered

- **Copy codex wholesale (sub-agent consolidation + git-repository memory folder + citation protocol)** — no. The consolidation sub-agent does not match our per-round cadence → downscaled to a structured call; change tracking uses the consolidation watermark, not git diff; the citation protocol would touch the host → "token ∩ answer" came first. Codex's *periodic full-corpus sweep* is adopted (phase 1); its *file-based memory + agent-grep recall* is not — that would discard our structured scope/category/BM25 retrieval, a genuine advantage codex lacks.
- **Anchors as the sole consolidation trigger (the first draft)** — no. Anchors are still a lexical signal: a reworded duplicate pair with no shared hard token never triggers, re-creating the exact "semantic decision gated behind a non-semantic metric" error the Problem names. The periodic full-corpus sweep is the completeness guarantee; anchors survive only as the per-round prefilter.
- **Triples / entity graph / canonical field** — no deterministic consumer; grouping and conflict candidates are covered by anchors + the full sweep, and the merge decision belongs to the consolidation judge reading full text. Canonicalization is itself unstable and LLM extraction variance would become a new dedup noise source.
- **Keep tuning the lexical metric (threshold/weights/Jaccard)** — no. Lexical similarity has a structural ceiling for "same fact, reworded"; moving the threshold only moves the error distribution (reworded corrections ≈0.02 vs distractors ≈0.06, see the calibration in the conflict-resolution residual note).
- **better-sqlite3** — no. The host engines floor (recorded in HOST_CONTRACT §11) guarantees `node:sqlite` on every supported host; a native module loaded into the host process risks an ABI/install hard-failure that kills the whole plugin. `node:sqlite`'s experimental API-drift risk is bounded by the minimal API surface behind `SqliteMemoryStore`. This is a plugin-distribution decision, not zero-dependency dogma.
- **SQLite FTS5 (replacing or paralleling BM25)** — no, and the listed behaviors were reproduced live on `node:sqlite`: the default `unicode61` tokenizer treats a contiguous CJK run as one token; `trigram` requires ≥3-char queries and misses the most common 2-char Chinese words; and node:sqlite exposes no FTS5 custom-tokenizer hook (a C API reachable only by a compiled extension via `loadExtension` — a heavier native dependency than better-sqlite3). At ≤500 short entries the in-memory BM25 scan is microseconds, so FTS5's disk-backed index gives no performance benefit, and a parallel index would add a shadow index plus two ranking systems to reconcile. The existing unigram+bigram tokenizer already solves CJK.
- **Moving entries into the host medium in a new format** — no. storage-json is a host peer contract; unilaterally changing the format breaks compatibility. SQLite enters as a plugin-owned local backend behind the `MemoryStore` abstraction. (`remote/` is an RPC adapter over the same memory service, not an alternative storage source; it rides the service abstraction, so a backend swap is transparent to it.)
- **SQLite first (the first-draft ordering)** — no. That order placed a full plumbing release that fixed none of the named defects ahead of the repair, and neither support held: the CI fsync symptom was dissolved by medium seeding, and "avoid two migrations" did not hold — the JSON side evolves by zero-migration optional fields and an absent-means-empty table, the consolidation state rides the meta table into SQLite with the single import, and the migration count is constant at one. Consolidation first repaired the 9/2 report's defects at minimal risk; SQLite afterwards kept its full value as an independent release.
- **Registering a SQLite StorageBackend on the host storage hub** — no. The host storage layer is backend-agnostic, but memory's composition row belongs to dsh-web-app, not this bundle (TECH_DESIGN §10.3) — attaching along that seam means coordinating a host change; the `MemoryStore` abstraction seam is plugin-owned with zero host change. If the host later ships an official SQLite backend, `SqliteMemoryStore` can be replaced by a bridge.
- **Redefining `accessCount` to "count only on answer overlap"** — no. The field is already consumed by `trimEntries` eviction order and the decay judgment; silently switching its semantics changes the meaning of standing data and ranking. The new `hitCount`/`lastHitAt` fields are zero-migration and semantically independent; the hit-first sweep ranking is the shipped combination.

## Consequences

- **Shipped verification** (`tests/consolidate.spec.ts`, `tests/sweep.spec.ts`, `tests/hit-signal.spec.ts`, `tests/store-contract.spec.ts`, `tests/migration.spec.ts`, `tests/write-path-rework-acceptance.spec.ts`; all fake-LLM, no test touches a real model): the consolidation selector's four signals, the fail-closed verdict protocol, all four actions' store writes, the zero-shared-anchor sweep fixture (measured overlap 0.24), the hit-signal opposing fixtures, the `markHits` accounting, the three-backend contract suite (73 cases), and the migration's three transition states over the real composition. `npm run build` + `npm run test` green at 945 passed | 6 skipped (the env-gated real-API judge suite).
- **The 9/2 baseline is mechanically countable now:** `duplicatePairCount` in `eval/mechanical.ts` (surfaced as `storage.duplicatePairs` in report slices) reads the audited duplicate-pair multiplicities from the report; the corpus-replay acceptance assertions (prog101 contradiction annotated, prog112 projectName, the consolidated shape reading 0 pairs) are pinned in vitest. The full harness replay and the v2 judged A/B remain the eval lane's gates.
- **Cost posture:** the per-round tier costs at most one LLM call per extraction batch (zero without candidates); the periodic sweep costs at most one call per startup + per N sessions under its meta-table cooldown; the hit signal costs no LLM calls at all. The extraction budget deliberately does not bound the sweep.
- **Bounded bias accepted:** an entry the model used without echoing its tokens is under-counted — the under-count only feeds consolidation selection order; decay/janitor never read `hitCount`, and `decayDays` remains the only forgetting knob.
- **Risks carried forward:** `node:sqlite` is experimental — API drift is bounded by the minimal surface behind `SqliteMemoryStore` and the HOST_CONTRACT §10 checklist item; the named fallback if it becomes unusable is better-sqlite3 behind the same `MemoryStore` seam, or reverting to `host-medium`. The kill switches (`consolidation: 'legacy-judge'`, `sweepEnabled: false`, `storage: 'host-medium'`) each revert a tier independently.
- **Deferred (phase 4):** the curated index view and the eval A/B re-baseline (write-amplification re-baselining under SQLite, host-medium-vs-sqlite per-scenario EQUAL) wait on phases 1–3 being stable and a v2 A/B baseline on record.
