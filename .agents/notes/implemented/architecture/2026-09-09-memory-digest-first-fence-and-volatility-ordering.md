# Agent Note: Memory injection goes digest-first — one-time inventory at the step tail, data sections ordered by volatility

Status: implemented

English | [中文](2026-09-09-memory-digest-first-fence-and-volatility-ordering.zh.md)

This note **rewrites rather than overturns** [the index-default promotion](2026-09-01-index-default-promotion.md). The value that promotion protected — the model's awareness that memory *exists*, without having to guess before searching — is inherited by the one-time digest's category counts and anchor topic words. What was cut is the 80-character per-entry existence lines and their residence in the frozen prefix: existence awareness now costs one ≈114–250-token message per session instead of a standing section that grows with the store.

## Problem

The index default parked the whole store's existence lines inside the frozen system-prompt prefix — data-register content at the position farthest from the question, invalidating the prefix tail on every compaction re-freeze, and paid on every turn even when no memory was relevant. A survey of OpenClaw's source (`~/openclaw`, the recorded investigation basis) established three principles that the index-shaped default violates:

1. **Instruction registers reside in a stable prefix; data registers do not.** OpenClaw's system prompt carries the memory behavior rules as tool-contract instructions ("Mandatory recall step: semantically search … before answering questions about prior work, …" — `extensions/memory-core/src/memory-tool-contract.ts:93`); the full corpus is reached by retrieval. Its standing MEMORY.md is a curated set promoted by recall signals, not a directory.
2. **Volatile content sorts to the prompt tail by descending volatility.** `src/agents/system-prompt.ts:87`'s `CONTEXT_FILE_ORDER` places the most-rewritten file (MEMORY.md) last, against the cache boundary — a change costs only the tail of the cached prefix.
3. **Truncation degrades into a retrieval pointer.** The truncation warning says "Treat Project Context as partial and read the relevant files directly if details seem missing" (`src/agents/bootstrap-budget.ts:219`) — the loss becomes an instruction, not a footnote.

Two measured defects sharpened the problem: the three section builders truncated by slicing the assembled text, eating their own closing fence tags (a truncated `<project-notes>` swallowed everything after it into the fence's scope, host tool guidance included); and the single notes budget let the conventions half starve the pitfall log to zero in real stores.

## Decision

**`memoryMode` defaults to `digest`** (rollback = one live settings field: `memoryMode: 'index'`). The injection surface splits by register:

- **Frozen sections carry instructions only.** In digest mode the `memory` section is the policy block plus a digest hint; the shared `MEMORY_POLICY_TEXT` stays mode-neutral so `policy-only` never claims an injection that did not happen. `full`/`index` remain explicit opt-ins with unchanged semantics.
- **Data rides the step tail.** The session's first pre-step appends one `<memory-digest>` message — per-project/per-scope category counts, an anchor-derived `Topics:` line, and a `[N entries; M stale hidden]` footer, within `memoryDigestCharLimit` (default 800, 0 = off). The per-session flag is set only after a non-empty emission (a live budget raise fires on the very next step); a clean `compaction/end` clears it, so the rebuilt prefix re-learns the store once. The digest is an inventory, not a recall: no `markRecalled`, no hit ledger. Notes-rendered entries are excluded by the same `isRenderedEntry` predicate the snapshot uses — no double injection.
- **`autoRecallEnabled` defaults to on** as the digest's complement: the digest answers *what is stored* (once), the `<recalled-memory>` fence answers *what it says* (per step, at the tail). The fence's search passes `recordRecall: false` and stamps its hits through `markRecalled(ids, 'fence')` — the new lightweight tier: `lastRecalledAt` refresh only, never an `accessCount` bump, because `accessCount` drives entriesCap eviction and BM25 query luck must not inflate it. The tool surface keeps the full stamp.
- **Sections are ordered by descending volatility.** `memory` 90 → **6000**, `project-notes` 91 → **6001** — after the host's tool guidance (`SECTION_ORDERS`: TOOL_* 1000–2900, TOOLS_SDK 5000) and before `DELIVERABLE_FILE_REFERENCES` (9000); `soul`/`user-profile` stay at 80/81. A compaction re-freeze that changes the memory/notes text now costs only the prefix tail (HOST_CONTRACT §3 records the measured orders).
- **Truncation closes its fence.** One shared `fenceWithin` helper backs `soul` / `user-profile` / `project-notes`: the budget is a whole-section cap, the helper reserves the fence overhead and the truncation footnote, cuts the body, and keeps the closing tag inside. The notes footnote degrades to a retrieval hint ("notes are partial; use memory_search for the rest"); soul/user keep a neutral footer (no read tool to point at — nothing fabricated).
- **Notes budgets split per kind** — `notesConventionsCharLimit` (1600) / `notesPitfallsCharLimit` (800) — so the pitfall log can no longer be starved. Moving budget application into `snapshotFor` made the notes module's settings read load-bearing and exposed its latent fiber defect (a plain `ctx.settings` access on a non-injected fiber throws, so the service silently rendered with builtin defaults); the service now reads through a settings-injected fiber, the identity plugin's pattern. Selection is entry-level at freeze time, ordered pinned → importance → `lastRecalledAt ?? updatedAt`; squeezed entries fold into per-section count lines, never silently dropped. The published `notesCharLimit` is deprecated, not deleted: when it is the only budget key set, both halves derive at 60/40 through `resolveNotesSettings` (schemastery's non-strict object passes the removed key through, so stored documents still read).
- **Anchors became a prompt surface and got both fences.** Store write paths (both backends) run each anchor through `scanContent` and silently drop violating or empty anchors — they are derived tokens, the entry body is untouched; the digest builder's per-anchor `redactBlocked` is the load-time second layer. This closes the SQLite backend's update path ignoring `input.anchors` entirely (it now applies the same absent-means-keep + filter semantics as the domain backend).

## Alternatives considered

- **Keep `index` as the default.** Rejected: it is the measured worst case for prefix residency — every entry's line sits in the frozen prefix all session, and the store's growth is paid on every turn. The existence awareness it buys is exactly what the digest inherits at one-shot cost.
- **A `systemPrompt.context()` dynamic channel (the v1 plan).** Rejected with the channel: it depended on host projection semantics (`RuntimeContextProjection`) that could not be verified against the installed peer, and per-turn re-freezing of the sections would have added a new KV-cache invalidation path. The step-tail message needs no host contract beyond `agent/pre-step`, which is already evidenced.
- **Per-turn re-freeze of the standing index.** Rejected: same invalidation cost as the channel, for data the fence already delivers per-step.
- **Digest as a standing section.** Rejected: it would re-create the residency problem one level down — counts and topics change whenever the store does.
- **Hit-ledger bookkeeping for the digest.** Rejected: the digest is not a recall; counting its lines as candidate hits would let every session's answer echo topic words into `hitCount`.

## Consequences

- **Standing prefix:** the digest-mode sections measure 434 ≈tokens (policy + hint) and the dual-budget notes section 466 ≈tokens over the golden fixture — versus index's 1102-token standing section — and both are byte-stable for the session's life (asserted directly in `tests/context-refresh.spec.ts`). The one-time digest message costs ≈114 ≈tokens over the 35-entry fixture (≈250 with anchor-heavy stores); tables regenerate via `DSH_MEMORY_EVAL_VERBOSE=1 npx vitest run tests/recall-golden.spec.ts`.
- **Recall-signal semantics, three consequences on record:** (1) the hit ledger's standing round now reflects the recalled set — when the fence fires, its hits replace the standing ledger for that round, so an answer can only echo what it actually saw; `hitSignalEnabled` stays default-off and sweep behavior is unchanged. (2) The janitor's decay clock is refreshed by lexical fence hits (`lastRecalledAt`), so a dormant entry that merely matches query words can survive longer — accepted as "recently presented" being true either way. (3) The notes ordering's `lastRecalledAt` signal is fed by these fence stamps, so a convention that happens to match queries floats up the notes budget — importance and pin still outrank it.
- **Notes budgets apply at freeze time:** a live budget change lands at the next `session/created` / clean `compaction/end`, not per assembly — the assembly-side `fenceWithin` cap is the final defense. Documented in the card hints and TECH_DESIGN §7.4.
- **`notesCharLimit` deprecation:** released in v0.9.1, so it degrades rather than deletes — the resolver derives 60/40 while the old key remains the only one set; each new key wins its own half. README's settings-migration note owns the user-facing story.
- **Anchors coverage bias:** entries without anchors contribute counts to the digest but no topic words, so anchor-poor stores get a sparser `Topics:` line (a high-IDF content-token fallback is a recorded future option). The defense inverted from "anchors never reach a prompt" to "write-time scan + load-time redact", matching the content/summary precedent.
- **Cross-process boundary, unchanged:** the digest reads the process-local store view like every other injection surface — a second writer's entries appear at its next freeze/step, not sooner.
- **Rollback is one live field** (`memoryMode: 'index'`), and the fence default is independently revertible (`autoRecallEnabled: false`) without touching the digest.
