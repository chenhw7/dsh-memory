# Agent Note: bundle 迁到 DSH 0.2 宿主契约

Status: implemented

[English](2026-11-25-dsh-0.2-per-entry-settings-and-client-page.md) | 中文

## Problem

DSH 0.2 换掉了本 bundle 赖以生存的几处宿主表面，0.9.x 包已经完全加载不起来：

- **设置失去了运行时读取**。`ctx.settings.installSection(...)` 与 `ctx.settings.get(ns)` 都被删除，`SettingsForms` 只剩表单/线协议面（`describe`/`update`/`replace`/`mutate`）。改为每个 profile 条目自己导出 `Config`、在 `apply(ctx, config)` 里拿到，卡片提交后宿主重跑该条目。
- **客户端设置传输被替换**。`ctx.settingsScope.bind({ namespace })` 与 `SettingsScopeSnapshot` 不复存在；Plugins 页不再有按命名空间分发的 `settings.plugin.item` 卡片槽，改为 `plugins.bundle.config` / `plugins.row.config`，由 `ctx.configForms.get(entryId)` 供表单。
- **更小的词汇面破坏**。`MessageSourceMap` 取消万能 `plugin` 类型（各生产者自声明）；tool 结果不再是内容块（`tool/result.data.message` 是 tool 角色消息）；`session.events` 不存在（同步读日志已废弃）；`sessionProjections.register` 变为可 await 并返回受支持的读句柄；`dsh-invariants` 整包移除；`ctx.tools.execute` 要求装配里挂 executor。
- **版本闸门**。0.2 在安装期就校验 `engines.dsh` / peer 范围，`^0.1.2-alpha.2` 的声明会直接拒绝安装，而不是留到运行时才炸。

真正有意思的不是机械移植，而是移植逼出的两个决定：当任何插件都读不到别人的设置时，共享旋钮放哪；当按命名空间分发的卡片槽消失后，配置界面放哪。

## Decision

**每个设置面一个条目，跨条目旋钮走拥有者的服务。** bundle 行被重命名，使**行 id 就是宿主寻址的设置命名空间**：`memory`（store）、`memory-tools`、`memory-review`、`memory-notes`、`memory-identity`、`memory-autorecall`（context）、`memory-remote`，加上保持不变的扫描器空操作行 `memory-root`。

| 条目 | `Config` | 发布 |
|---|---|---|
| `memory` | 存储后端、`entriesCap`、`crossProcessProbeMs`，以及注入/召回切片（`memoryMode`、`memoryPolicyCustomText`、`memoryCharLimit`、`memoryDigestCharLimit`、`memoryMaxEntries`、`maxSearchResults`、`decayDays`） | `ctx.memory.settings()` |
| `memory-autorecall` | `autoRecallEnabled`、`autoRecallLimit`、`autoRecallMinChars`、`hitSignalEnabled`、`hitSignalThreshold` | — |
| `memory-notes` | `notesEnabled`、两个预算、`notesMaxEntriesPerFile` | `ctx.projectNotes.settings()` |
| `memory-identity` | `identityEnabled`、`soulCharLimit`、`userCharLimit`、`identitySeedDir` | `ctx.identity.settings()` |
| `memory-review` | review/提取/curator/sweep 切片，含 `confirmBeforeWrite` | `ctx.memoryReview.settings()`（新增的最小面） |
| `memory-tools` | `scannerAllowlist` + 检索上限的组合兜底 | —（读上述四个服务） |

注入预算落在 store 条目上，因为 `ctx.memory` 是所有兄弟插件本来就解析的、唯一的记忆服务；`confirmBeforeWrite` 留在 review 条目上，因为 review 页面拥有那个字段、工具只是执行者。`MemoryStore`、`ProjectNotesService`、`IdentityService` 各自新增 `settings()`，因此卡片写进去的值由声明它的插件读回来。

**配置界面是一个 bundle 页面，不是五张卡片。** `src/client/index.ts` 只向 `plugins.bundle.config` 注册一个贡献，key 为 `@chenhw7/dsh-memory`，用 `ctx.configForms.whileServed([...条目 id])` 门控；页面渲染五个可折叠 section（`MemoryPluginCard.tsx` → `MemorySection`，`NamespaceCard.tsx` → `NamespaceSection`），每个 section 拿到自己条目的 `ConfigForm`。保存把整段草稿作为**一次** `mutate(ops, revision)` 提交——一个 revision 栅栏、一次宿主校验、一次恢复读取——而不是每个改动字段各写一次。

移植中的三个衍生决定：

- **消息来源自己声明，不借用。** `src/sources.ts` 用模块增强往 `MessageSourceMap` 里加 `memory-context` 与 `memory-review`。step 尾部消息用 `form: 'snapshot'` 并给出具名 `sections`（`memory-digest`、`recalled-memory`），因为后一轮围栏取代前一轮的集合；提取提示不带 form，因为它从不进入会话表面。
- **压缩 flush 自建日志。** `session.events` 既已消失，`memory-review` 就维护一份有界的 per-session 表（seq→文本，上限 500）加 `compactionId`→`shadowedSeqs`，由它本来就跑的全局 `session/event` 监听器填充，全程不碰已废弃的同步读。
- **冻结的提示词快照惰性重建。** 设置变更会重启该条目的 fiber，per-session `WeakMap` 随之清空。因此 context 插件在首次触达时冻结（`snapshotOf`），而不只在 `session/created` 冻结——运行中会话的记忆/笔记/身份段落不会在下一个会话开始前变空。

## Alternatives considered

**保留一个共享的「memory 设置」命名空间、跨插件读它。** 做不到：0.2 完全没有跨条目设置读取，而用 `ctx.settings.describe()`（面向 UI、已脱敏、带 revision 的视图）重建一条读取路径，等于把配置读取绑死在一个为表单而生的线协议上。

**在 context 条目上保留一个巨型 `Config`**（0.1.x 的组合形状），其他行通过 context 发布的服务拿到自己的切片。否决：这会把 store 的后端旋钮搬进提示注入插件，且五个设置面里有四个没有拥有者，设置页根本无从寻址。

**按行注册 `plugins.row.config` 页面**，而不是一个 bundle 页面。这是宿主的逐行形态，也更接近旧的四张卡，但行页面的标题来自 `readPluginMeta(specifier)`——即 `<specifier>/locale/<lang>.json` 的 `meta.title`——于是每个子路径都要自带 locale 资源与 exports 条目，五个小页面还要各自重复同一套保存/丢弃界面。bundle 页面只维护一份字典和一个页面。

**走 `plugins.item`。** 该槽位的文档明确写着被官方设置页占用，并把 bundle 自己的配置指到 `plugins.bundle.config` / `plugins.row.config`。

**用「扫描会话里是否已有 digest 消息」保住重启后的 digest 标记。** 否决：为了一个罕见事件在长会话上付每步扫描的成本；代价记录在 Consequences 里。

**用双路径适配层同时兼容 0.1.x。** 否决：设置模型、消息来源词汇、客户端传输三处都换了形状，适配层等于要实现两套宿主契约并为两套都维护测试——维护者选择干净的 0.2-only 线（0.10.0 破坏性发布），0.9.x 留给 0.1.x 宿主。

## Consequences

- **改行名就是改设置条目。** 升级后，旧 id（`memory-store`、`tool-memory`、`memory-context`）下的用户覆盖不再生效。行 id 现在是稳定契约，写在 `cordis.patch.yml` 里。
- **`./invariant` 子路径消失**（`dsh-invariants` 已不存在），引用它的消费者必须去掉该 import。
- **设置变更可能重发一次 digest。** `digestSent` 标记活在 fiber 的 `WeakMap` 里，重启即丢，下一步可能重发一次库存清单。接受：设置变更罕见、消息走 step 尾部（从不进缓存前缀），而要做成持久标记就得每步扫一次会话。
- **`zod` 钉在宿主的精确版本（4.6.6）。** `domainTable` 的 schema 类型必须与 storage-domain 看到的是同一个实例；caret 范围会解析到更新的补丁版并产生第二份副本，`domainTable(...)` 处直接类型失败。升级 devDeps 时要重新钉。
- **测试装配必须挂工具执行器。** `@deepseek-ai/dsh-tool-executor-native` 成为 devDependency，工具用例挂上它；没有它 `ctx.tools.execute` 直接 `ToolExecutorUnavailableError`。
- **GUI 回归风险真实但有界：** 页面的字段、草稿与 revision 栅栏保存只由客户端类型闸门与手工使用覆盖——旧的逐卡布局同样没有浏览器测试。
- **换来的：** bundle 能在 0.2.x 上加载并保持可安装；配置面是一个页面一份字典；设置切片与拥有它的插件同处一处；所有读取路径上不再有已废弃的宿主 API（没有 `session.events`、没有 `installSection`、没有 `settingsScope`）。

## Testing

`npm run build`（宿主 `tsc` + 客户端闸门 + esbuild 打包）与 `npm run test`（vitest，含集成装配用例）把守本次变更；工具用例挂 native executor，装配用例通过 `apply` 走每条目的配置。
