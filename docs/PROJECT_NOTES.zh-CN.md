# 方案设计：Project Notes —— 项目级文件形态记忆（编码习惯 + 踩坑日志）

| | |
|---|---|
| Package | `@chenhw7/dsh-memory` |
| 状态 | **已实现（v0.2.0）** |
| 范围 | 在现有 bundle 上新增一个 `memory-notes` 组合行；`memory-review`、`memory-context` 小幅扩展 |

---

## 1. 目标与范围

dsh 主要用于代码编写场景。本方案在现有长期记忆能力之上，为每个项目仓库提供**文件形态的项目记忆**：

- 仓库内有一组专门的文件，记录**编码习惯/约定**与**踩坑日志**，可被 git 管理、在 PR 中 review、人可直接阅读。
- 每次会话开始时，这些文件的内容被自动注入 system prompt。
- 自动沉淀：
  - 检测到"同一类操作**连续失败 ≥2 次、最终成功解决**"的序列时，自动产出一条结构化踩坑记录。
  - 检测到用户**明说**（"记住/以后都……"）或**重复出现**的编码偏好时，自动更新到编码习惯。
- 非目标：语义检索、thoughts/调研日志、`~/.dsh` 之外的全局文件同步。

---

## 2. 现状核查（设计的事实基础）

对当前代码库（v0.1.x）的核查结论：

- **数据模型已具备所需 category**：`convention` / `preference` / `failure` / `procedure` 都是现成的记忆分类（`src/store/index.ts` 中 `memoryEntrySchema`）。本方案不引入新的记忆种类，只引入新的**载体（文件）**与**新信号（失败→解决序列）**。
- **现有存储在仓库之外**：全部记忆落在 `~/.dsh/storages/memory.json`，不进 git、不可读、无法共享。
- **现有踩坑信号噪声高且无配对信息**：`src/review/accumulator.ts` 对**每一次** `tool/result` 错误都收一个候选（包括敲错的 bash 命令），且提取时看不到"该失败后来是否被解决"——沉淀下来的"踩坑"多为失败碎片，价值低。
- **dsh 内核不自动注入 AGENTS.md**：AGENTS.md 仅在子目录变更时以 `agent.inject` 形式提示，没有 system prompt 级别的自动加载，因此本插件自建注入路径不会重复。
- **项目根可解析**：`session.header?.cwd` 已在 `inferProjectName` 中使用（`src/review/extract.ts`），写文件可用同一来源定位项目根。
- **注入采用冻结快照模式**：`memory-context` 在 `session/created` 冻结快照，保证 KV-cache 前缀稳定。文件注入沿用同一模式。

## 3. 决策记录（ADR）

### ADR-1：在现有插件内扩展，而非新建独立插件 ✅

新建 `src/notes/` 模块 + subpath 导出 `@chenhw7/dsh-memory/notes`，在 `cordis.patch.yml` 增加第七个组合行 `memory-notes`。

理由：

1. **数据依赖拆不开**：文件是 KV store 的渲染视图（ADR-2），真相源在本包。独立插件仍需 peer-depend 本包，凭空多一条跨包 API 边界。
2. **管线复用**：streak 信号长在 `accumulator`、pitfall prompt 长在 `extract`、导出去重/审计/衰减全部在 store——拆出去等于复制整条 review 管线。
3. **组合行机制正为此设计**：用户安装/卸载仍是一条 `dsh plugin add/remove`；不想要本功能的用户通过设置关闭。
4. **维护面减半**：peer-dep 范围、版本号、settings 命名空间各一份。

仅当"文件笔记需要脱离记忆管线单独分发"时才值得拆——ADR-2 选定 KV 为真相源后，该前提不成立。

### ADR-2：KV 为真相源，文件为只读导出 ✅

- 渲染口径：`KV store → markdown 文件`，**单向**。exporter 是唯一写者，天然无并发冲突。
- **现成的 dedup、LLM judge、janitor 衰减、审计、管理 UI 全部自动生效**——条目被 janitor 删除后，下次渲染文件自动瘦身，生命周期管理无需在文件层重做。
- 文件整体托管（文件头声明 "auto-generated, do not edit by hand"）；手写约定请写在 `AGENTS.md`，插件只维护其中一行托管指针（ADR-3）。
- **明确不做"文件 → KV"反向同步**：从仓库读到的内容绝不自动写回记忆库，防止克隆的恶意仓库通过 AGENTS.md 注入指令。文件只走 `文件 → prompt` 单向。

### ADR-3：文件布局 = 独立目录 + AGENTS.md 指针 ✅

```
<repo>/
  AGENTS.md                  # 仅 ensure 一个托管指针块（见下）
  docs/agent-memory/         # notesDir，可配置
    CONVENTIONS.md           # 编码习惯/约定
    PITFALLS.md              # 踩坑日志
```

不直接写 AGENTS.md 正文的原因：AGENTS.md 是用户与其他工具共有的文件，渲染覆盖风险高；独立目录是插件专用，可整块托管，且分文件便于独立控制上限。AGENTS.md 中只 ensure 一个指针块，供其他会自动读取 AGENTS.md 的工具（如 Kimi Code）发现：

```markdown
<!-- dsh-memory:begin -->
> Agent-maintained project notes live in `docs/agent-memory/` (auto-generated by dsh-memory — do not edit those files by hand).
<!-- dsh-memory:end -->
```

### ADR-4：踩坑条目粒度 = 结构化短条目 ✅

每条踩坑记录包含：症状（错误信息）、根因、修复方法，两三行内。不记录完整 diff/日志，避免文件与注入膨胀。

### ADR-5：习惯提取基调 = 保守 ✅

preference/convention 类记忆仅在满足以下任一条件时入库：用户明确要求（"记住/以后都……"等 keyword 信号），或同一偏好主题在本会话/历史记忆中**出现 ≥2 次**。单次场景性偏好不入库。

## 4. 数据流

```
session 事件
  → accumulator（新增 streak 信号 §5）
  → 阈值触发 LLM 提取（pitfall 专用 prompt + 习惯 admission 规则 §6）
  → scanContent 安全扫描 → dedup 预筛 → LLM judge → store（KV，真相源）
  → exporter 监听变更，debounce 渲染 CONVENTIONS.md / PITFALLS.md（原子写 §7）
  → 每个 session 的 session/created：snapshotFor 从 KV 同步渲染（顺带触发异步落盘）、冻结、注入 <project-notes> section（§8）
```

渲染采用显式的 scope×category 矩阵——**编码习惯是可以跨项目的**，因此文件不是 scope 的简单划分，而是把全局/个人层与项目层叠加渲染：

| 文件分节 | scope / category 过滤 |
|---|---|
| `CONVENTIONS.md › ## 项目约定` | 当前项目 `project` scope，category ∈ {`convention`, `preference`} |
| `CONVENTIONS.md › ## 全局实践` | `global` scope，category ∈ {`convention`, `preference`} |
| `CONVENTIONS.md › ## 个人习惯` | `user` scope，category ∈ {`preference`, `convention`} |
| `PITFALLS.md › ## 本项目踩坑` | 当前项目 `project` scope，category ∈ {`failure`, `procedure`, `tool-quirk`} |
| `PITFALLS.md › ## 环境与跨项目的坑` | `global` scope，category ∈ {`failure`, `procedure`, `tool-quirk`} |

"当前项目"由 `session.header.cwd` 的 basename 与条目 `projectName` 比对确定（沿用现有项目自动识别口径）。

分节顺序即优先级提示：**同一主题冲突时，作用域越近（项目 > 全局 > 个人）越优先**，注入文本中附带该说明。其他 category（如 `insight`、`correction`）不进 notes 文件，继续只走 KV 记忆注入。

**生命周期说明**：janitor 只衰减 `project` scope 条目，个人/全局习惯永不自动消失；重要的项目约定可通过现有 `memory_pin` / `memory_unpin` 钉住免于衰减，文件渲染自然尊重该语义。

## 5. 信号层：失败连续段（streak）检测

修改 `src/review/accumulator.ts`，以**成对序列**取代"每次 tool 失败都收候选"：

- **签名分桶**：`signature = toolName + normalize(args)`。
  - shell 类工具：命令的前两个 token（如 `npm test`、`pnpm build`）。
  - 文件类工具：目标文件路径。
  - 其他工具：仅 toolName。
- **状态**：projection state 新增 `openCalls`（`callId → { name, signature, seq }`，用于 call/result 配对）与 `openStreaks`（`{ [signature]: { count, lastErrorText, firstSeq, lastSeq } }`），均为 plain JSON。projection `stateVersion` 由 1 升到 2。
- **规则**：
  - 同签名 `tool/result` 带 error → `count += 1`，更新 `lastErrorText`（截断 ~500 字符）。
  - 同签名 `tool/result` 成功：
    - 若 `count >= pitfallStreakThreshold`（默认 2，可配置）→ emit 一个 `pitfall-resolved` 候选，内容含：工具/签名、失败次数、最后错误文本、成功调用摘要（命令或文件路径）、首尾 seq。
    - 若 `0 < count < threshold` → 仅清除该 streak，不产候选。
  - 桶数量上限（默认 8，超出按最久未更新淘汰），保证 projection 体积可控。
- **一次性失败不再进入周期 review 候选**——降噪的有意取舍。兜底：`compaction/end` 与 `session/disposed` 的 flush 提取仍扫全量事件，真正重要的一次性失败仍有机会被捕获。
- 现有 `keyword` / `correction` 信号不变。

## 6. 提取层

### 6.1 Pitfall 专用 prompt

对 `pitfall-resolved` 候选使用独立 `PITFALL_SYSTEM_PROMPT`，输出结构化短条目（ADR-4），强制 `scope: project`、[pitfall] 前缀：

```
project: [pitfall] 症状：运行 vitest 报 "Cannot use import statement outside a module"；根因：依赖未按 ESM 转换；修复：vitest.config.ts 中 server.deps.inline 加入该依赖。
```

### 6.2 习惯 admission 规则（保守）

`REVIEW_SYSTEM_PROMPT` 增补规则：

- preference/convention 类仅在用户明确要求或同主题重复出现时保留（ADR-5）。
- **scope 路由规则写死**（防止同一习惯在 user/global/project 间摇摆）：编码习惯/偏好默认落 `user`（跟随个人跨项目）；与用户个人无关的跨项目通用工程实践、环境/工具行为落 `global`；仅当前仓库成立的落 `project`。该规则同步增补进 `MEMORY_POLICY_TEXT` 的 "Memory write targets" 说明，使模型工具写入与自动提取两条路径口径一致。
- 复用现有 `[procedure] ` 前缀剥离机制，扩展 `[convention] ` / `[preference] ` / `[pitfall] ` 三个 tag → 分别落到 `convention` / `preference` / `failure` category（`storeMemories` 中现有 tag→category 逻辑自然扩展）。
- 已显式给出 category 的条目不再套用整批 `correction` 推断。

## 7. Exporter：`memory-notes` 插件（新模块 `src/notes/`）

- **renderer**：读取 `ctx.memory`，按 §4 口径过滤、按 `updatedAt` 倒序渲染。
  - `CONVENTIONS.md`：按 §4 矩阵分三节 `## 项目约定` / `## 全局实践` / `## 个人习惯`，bullet 列表。
  - `PITFALLS.md`：分两节 `## 本项目踩坑` / `## 环境与跨项目的坑`，条目原样输出（prompt 已保证结构化句式），按 `createdAt` 注明日期。
  - 文件头注明 auto-generated；每文件条目数 cap（默认 100，超出按最旧截断）。
- **writer**：`tmp + rename` 原子写；自动创建目录；ensure AGENTS.md 指针块（不存在 AGENTS.md 则创建一个只含指针块的文件；可用设置关闭）。
- **挂载点** `memory-notes`：插件注册 `projectNotes` service（`ctx.projectNotes`）；触发时机 = `memory-context` 在 `session/created` 调用 `snapshotFor(cwd)`（同步渲染顺带 reconcile）+ 本插件在 `agent/pre-step` 上基于 `memory.health().lastActivityTs` 的脏检查（带 debounce）。无需改动 `memory-review` 内部，完全解耦。
- **cordis.patch.yml** 增加第七行：

```yaml
- insert:
    - id: memory-notes
      name: '@chenhw7/dsh-memory/notes'
```

## 8. 注入：`project-notes` system-prompt 段

- `memory-context` 中新增 section：`name: 'project-notes'`，`order: 91`（紧邻 memory 的 90）。
- 注入内容 = `projectNotes.snapshotFor(cwd)` 的**同步渲染结果**：`session/created` 时 memory-context 调用 service，service 从 KV store 同步渲染并顺带触发异步落盘（同一份文本），返回值直接冻结到 per-session 快照；注入时按 `notesCharLimit`（默认 4000）截断。section 文本函数每次组装时读取冻结副本（KV-cache 前缀稳定，行为与现有 memory section 一致）。
- 注入不读文件——注入与落盘同源，prompt 内容与磁盘文件天然一致，不存在先写后读的时序窗口。文件只是人可读 / git 可管的导出视图。
- 无 cwd（当前项目不可解析）时：项目分节缺席，个人/全局分节照常渲染注入；且不向磁盘落盘（没有项目根可写）。
- 禁用或 store 缺失时注入空串（section 自动消失）。
- **会话内更新下个会话生效**——与现有 memory 注入语义一致，是有意取舍。

**与现有 `memory` section 的关系（关键：不是第二套记忆）**：notes 文件与 memory section 源自**同一个 KV store**，文件只是同一真相源的常驻注入视图，因此不存在双写不一致。两个重叠点的处理：

- **防重复注入**：`notesEnabled` 为 true 时，`readMemorySnapshot` / `readMemoryIndex` 排除已进入 notes 渲染矩阵的条目（§4 的 scope×category 范围），`full` / `index` 模式下同一内容不在 prompt 中出现两次。默认 `policy-only` 模式不注入记忆内容，天然无重叠。
- **注入与落盘同源**：注入用的是 `snapshotFor` 的同步返回值，落盘是同一份文本的异步原子写（skip-if-unchanged）——不存在"先写完文件再读回"的顺序依赖，reconcile 与冻结一次调用同时完成。
- **路由说明**：`MEMORY_POLICY_TEXT` 增补一句——习惯/约定/踩坑已在 notes section 中，其余（纠错、洞察、环境事实）走 `memory_search`。

## 10. 安全与边界

- 所有入库内容仍走 `scanContent`（secrets / prompt-injection / exfiltration 模式），exporter 渲染前内容已过关，不重复扫描。
- **文件 → KV 反向同步不做**（ADR-2），杜绝克隆仓库注入。
- 导出的文件进入 git 后即视为用户自有内容；对其他工具而言它们只是普通 markdown。
- Headless profile 行为与现有 bundle 一致（需自行补 storage 行，README 已文档化）。

## 11. 已知限制与后续可选

- **多机/团队共享**：KV 是每台机器的真相源。若把生成文件提交进 git，多台机器各自的 render 会互相覆盖（后渲染者赢）。本期不做合并；可选缓解：(a) 将 `docs/agent-memory/` 加入 `.gitignore`；(b) 后续实现"收养"机制——渲染前把文件里不在 KV 的条目经 scanContent + dedup 收养回 KV（本期范围外）。
- 无向量检索、无文件级版本历史（依赖 git 即可）。
- 会话内写入不刷新当次注入（§8）。

## 12. 测试计划

- **streak 检测**（扩展 `tests/accumulator.spec.ts`）：签名归一化用例；失败×2+成功 → 恰好 1 个 `pitfall-resolved` 候选；失败×1+成功 → 0 候选；不同签名互不配对；桶上限淘汰。
- **提取**（扩展 `tests/extract.spec.ts`）：新 tag 剥离（[pitfall]→failure 等）；pitfall prompt 输出解析。
- **exporter**（新增 `tests/notes.spec.ts`）：渲染口径过滤（项目/全局/个人三层叠加 + 当前项目隔离、其他 category 不进文件）；条目 cap 截断；AGENTS.md 指针块幂等 ensure；原子写。
- **注入**：`buildNotesSectionText` 文本构建（双空 → 空、零预算 → 空、截断）；snapshot/index 互斥过滤；service `snapshotFor` 的分片渲染 + 落盘内容 + 无 cwd 口径。
