## 2. 演进目标

北极星：一个满足以下特性的记忆子系统：

- **可检索** —— 需要时正确的记忆浮现：模型能看见存了什么，词法检索能找到它；
- **健康** —— 无重复、无腐化（去重、生命周期、质量评分）；
- **智能** —— 提取在廉价算力上持续改进（专用模型、更丰富的信号）；
- **可运维** —— 可观测、用户可管理、存储可替换。

以下每一项都保持四行 bundle 形态，以安全默认值扩展 `memory` 设置命名空间，让新的写入
路径全部经过 `scanContent`，并使后台工作对 agent 循环保持非阻塞。

## 3. 路线项目录

### 3.1 测试基础设施补全 — P0 — ✅ 已实现（`5fb7a37`）

- **为什么：** 规格测试套件（8 个文件、约 120 个用例）已存在，但 vitest 尚未接入
  `package.json`（`test` 是占位符），且缺少宿主级集成覆盖。
- **怎么做：** 将 vitest 加入 devDependencies；`test` → `vitest run`；在 push/PR 时运行
  `build` + `test` 的 CI 任务；一个集成规格：启动真实的 Cordis 组合（临时 `$DSH_HOME`
  上的 `storage-domain` + `storage-json`），端到端演练四行 bundle（add → search →
  update → remove，外加一次压缩冲刷）；为 `parseExtractedMemories` 与 `scanContent`
  建立黄金数据集。
- **完成标志：** `npm test` 在 CI 中通过；集成规格覆盖完整组合；扫描器与解析器拥有基于
  语料的 FP/FN 回归检查；日志卫生用例证明插件绝不向会话日志引入未知事件类型（完整记忆
  活动 → 冲刷日志 → 重新加载会话 → 断言干净恢复——无宿主改动策略的护栏，见 §6）在锁定的
  dsh 发布线上通过。

### 3.2 插件自有审计存储 — P0 — ✅ 已实现（`5fb7a37`）

- **为什么：** 审计轨迹与 UI 需要回答"学到了什么、来自哪里、为什么"——但在无宿主改动
  策略（§5、§6.1）下，把它写进*会话日志*已不可行：宿主持久化读取路径拒绝重新加载包含白名单
  之外事件类型的存储日志，白名单 `KNOWN_SESSION_EVENT_TYPES` 只由仓库内声明生成（`ignorable`
  标记是唯一的逃生口，而它是读取侧字段——`Session.append` 从不设置它，故插件追加的事件恒为
  required），已安装依赖中不存在注册插件类型的运行时接缝，`Session.append` 也不提供写入侧
  `ignorable`。因此审计轨迹存放在插件自己的存储中，绝不进入会话日志。
- **怎么做：** 在插件自有的 `memory` 域中新增第二张表（`audit`），在现有域规格里与
  `entries` 并列声明。**保持域版本为 0**——不要 bump：storage-json 的 `parse` 路径会拒绝
  任何戳记版本与规格不符的介质（`version-mismatch`），且 `DomainFacility.open` 不暴露任何迁移
  步骤，因此 0 → 1 的 bump 会让每个存量用户的 `memory.json` 直接拒绝加载且无恢复路径。表集合
  不受版本约束：`open` 时 storage-json 只读取 descriptor 声明的表，将文件中缺失的声明表初始化
  为空 map、忽略文件中多出的表——因此在 v0 规格上新增 `audit` 是零迁移、前向兼容的变更。每次
  成功变更后——工具 `memory_add` / `memory_replace` / `memory_remove` 以及评审/冲刷提取写入——
  追加一条记录：`{ op, entryId, scope, category?, source: 'tool'|'review'|'flush'|'ui',
  sessionId?, ts, contentPreview（约 100 字符，仍经 `scanContent`） }`。记录在追加时确定性裁剪
  （保留最新 N 条，默认 200），审计表不会无限增长。`memory/*` 的 `SessionEventMap` 声明保留为惰性
  预留类型——v0.x 中无任何代码发出它们。
- **完成标志：** 每条写入路径（工具、提取、UI）恰好追加一条审计记录；审计表永不超出上限；
  §3.1 日志卫生用例通过（高强度记忆活动后会话仍可干净恢复）。

### 3.3 词法检索增强 — P1 — ✅ 已实现（`f5bfecc`）

- **为什么：** 把原始查询串当作一整段子串去匹配，只要查询与条目"共词但不逐字成句"就会
  失败；多词查询中任何一个词错位就会整体落空。在这个条目规模下，召回是一个词法组织
  问题，而非语义问题。
- **怎么做：** 保持 `MemoryStore.search` 为对内存条目的 O(n) 扫描——无索引、无向量：
  (1) 对查询分词（大小写折叠；按词边界切分，CJK 逐字符匹配）；(2) 只要*任意*一个词命中
  即匹配该条目（OR 语义），不再要求整段子串；(3) 按词命中数排序，其次按新近度
  （`updatedAt`）。结构化过滤与工具 schema 保持不变；无新表、无迁移。
- **完成标志：** 在 §3.1 的固定评测集上，黄金查询的召回优于子串基线；在我们目标的条目
  量级（几十到几百条）延迟不变。

### 3.4 去重与合并管线 — P1 — ✅ 已实现（`c4b7977`，LLM judge `6474f08`）

- **为什么：** 评审提示词只是*要求*模型省略已知记忆，但存储是直写的，近似重复会不断
  积累。
- **怎么做：** 仅在提取路径上、`add` 之前：(1) 对当前快照做廉价预过滤（归一化词元的
  Jaccard 相似度，含英文 + 中文停用词过滤——不使用 embedding，见 §5）；(2) LLM 裁决给出
  重复 / 更新 / 新建 三值判定（每次预过滤命中触发一次短调用，而非每个候选都调用；裁决
  提示词将已有内容与新候选并列呈现；尽力而为，任何失败安全回退到合并）；(3) 判为重复时 →
  `update`（合并内容、刷新 `updatedAt`）；判为更新时 → `update`（用新内容替换旧内容）；
  判为新建时 → `add`（创建独立条目——预过滤是假阳性）。
  模型主动发起的 `memory_add` 保持显式（意图优先）。`judgeEnabled` 设置（默认 `true`）控制
  LLM 裁决是否运行；关闭时预过滤命中直接合并（judge 之前的行为）。
- **完成标志：** 在一个合成重复数据集（≥ 50 条种子事实，每条用近义改写 3 次，另加 ≥ 50 条
  真正互异的事实作为对照，纳入 `tests/fixtures/dedup-dataset.ts`）上，管线后重复率 **≤ 5%**，且对种子集
  的不同事实保留率（精确率/召回率报告）**≥ 95%**。LLM 裁决正确区分预过滤无法区分的"同模板不同主题"
  对（如"项目使用pnpm" vs "项目使用vitest"）；中文停用词过滤防止不相关中文句子共享过多词元。
  数据集、阈值与中文专项测试共同构成门槛。

### 3.5 记忆生命周期 — P2 — ✅ 已实现（`b31de0e`）

- **为什么：** 当前记忆只能手工删除；过期条目劣化检索并消耗提示词预算。
- **怎么做：** 按作用域的衰减策略（例如：project 作用域条目在 N 天未被召回后衰减；
  `user`/`global` 持久保留）、`supersedes` 链接（新条目使旧条目失效）、置顶（免疫
  衰减），以及一个确定性的清道夫（janitor）过程（在 `session/created` 或定时器上），
  每个动作都记录到 §3.2 审计存储。
- **完成标志：** 衰减绝不触碰置顶或 `global` 条目；清道夫行为有日志记录，可从审计存储
  复查。

### 3.8 记忆管理 UI — P1 — ✅ 已实现（`fba5a55`，宿主集成 `cf39b8d`）

- **为什么：** 今天数据只能通过工具和 JSON 文件浏览；用户需要一等公民的视图与编辑器。
  纯设置命名空间做不到这一点：`installSettingsSection` 注册的是 JSON 设置命名空间（仅表单
  字段），且 `settings.*` RPC 仅限本地回环（loopback）。
- **怎么做：** 一等数据视图是一个**客户端插件**，打包在同一个 npm 包内（零宿主改动）：在
  `package.json` 声明 `dsh.client`（`platform: 'web'`）并导出 `./client`——宿主的客户端模块
  注册表会在 `/plugins/<id>/client.js` 提供它（宿主文档：`docs/subsystems/client-modules.md`）。
  该 bundle 注册 `settings.section`（或 `settings.plugins.tab`）插槽，组件为任意 React：按
  作用域浏览（卡片含 id、category、时间戳）、搜索框、新增 / 编辑 / 替换 / 删除，i18n 走
  locale 插槽。数据访问走 **Typert API 网关**：用一个小的 `TypertRemoteService` 包装把
  `MemoryStore` 的读写暴露为 `@Remote` 方法（委托给 `ctx.memory`，写入仍然经过存储契约的
  扫描与写序列化），UI 侧以 `ctx.remote.memory.*` 调用（宿主文档：`docs/api-gateway.md`）。
  先例：`ui-agent-preset` 的 `AgentPresetSection`（RPC 驱动的卡片列表、删除、只读查看器）。
  同一区域渲染**记忆活动面板**——基于 §3.2 审计存储的时间线（来源、作用域、预览、时间戳），
  作为提取触发的写入（从不经工具卡片）的用户可见答案。
- **验证注意事项（✅ 已在 `~/deepseek-harness` 中验证）：** 客户端模块 manifest 字段
  （`dsh.client`）、`/plugins/<id>/client.js` 服务路径、`@Remote` 网关、`settings.section` 插槽
  全部**在锁定的宿主 checkout 中确认**——`docs/subsystems/client-modules.md`（manifest + 服务路径）、
  `docs/api-gateway.md`（`@Remote` + `TypertRemoteService` + `ctx.remote.*`）、
  `packages/client/ui-settings/src/client/contract/slots.ts`（`settings.section` 插槽，`kind: 'list'`，
  `scope: 'root'`）。确认的真实先例：`dsh-message-feedback`（`MessageFeedbackService`——侧表 CRUD，
  最接近的类比）、`dsh-goal`（`GoalService`——活 Agent `@Remote`）、`ui-agent-preset`（设置区域注册，
  任意 React TSX 经 `ctx.slots.inject('settings.section', ...)`）。

  **验证中发现的约束（原方案未提及）：**
  1. **需要修改宿主代码库：** `@Remote` 服务的客户端面必须在 `packages/api/remotes/src/client/index.ts`
     中挂载（import + `ctx.remote.$mount()` + peerDependency）。这是宿主代码改动，与 §6 无宿主改动
     策略冲突。§3.8 因此被阻塞，直到宿主团队接受对 `dsh-api-remotes` 的 PR，或策略放宽。
  2. **`dsh.client` 在装配包上**（`@deepseek-ai/dsh-api-remotes`），不在记忆插件包本身上。插件
     只需要 `exports["./typert"]` 和 `exports["./remote"]` 子路径。
  3. **Typert 代码生成：** `lib/typert.host.js` 和 `lib/typert.remote-client.js` 由宿主构建管线
     （`tsdown` + `typertPlugin`）自动生成，不能手写。插件必须纳入宿主 workspace 才能被生成器发现。
  4. **写方法应钉死在 loopback**——通过 `packages/client/connection/src/index.ts` 的
     `PRIVILEGED_METHODS`；`trustedHosts` 是 DNS 重绑定围栏，不是认证；不钉死的话 LAN 调用者可以
     访问变更性记忆方法。
  5. **UI 插槽注册：** `ctx.slots.inject('settings.section', () => ctx.slots.register({
     name: 'settings.section', id: 'memory', order, label, locale, inject }, Component))`——
     组件为任意 React TSX，接收 `{ close }` + 框架 hooks。
- **完成标志：** 完整 CRUD 往返经 `ctx.remote.memory.*` 完成；变更在下一个会话的快照中
  生效；活动面板显示提取触发的写入；`@Remote` 服务已挂载到 `dsh-api-remotes`，写方法通过
  `PRIVILEGED_METHODS` 钉死在 loopback。

### 3.11 跨会话一致性 — P2（探索性）— ✅ 纯检测器（`6a92bbc`）

- **为什么：** 记忆可能与用户当前陈述或更新的证据冲突。
- **怎么做：** 在上下文组装时，可选地检测与当前会话所述事实冲突的条目（对标记的条目对
  做 LLM 裁决），并将其在快照中渲染为 `stale` / `conflicting`（"记忆与当前证据冲突"），
  而非静默覆盖。
- **完成标志：** 冲突被呈现给用户，且解决（保留 / 替换）是显式的。

### 3.12 有界存在性索引（L1-lite）— P1 — ✅ 已实现（`f5bfecc`）

- **为什么：** 默认 `policy-only` 模式只告诉模型工具有存在，却不告诉*存了什么*；模型只能
  靠猜关键词调用 `memory_search`，而关键词猜错就意味着记忆漏召回。可见性是一阶召回
  问题；匹配是二阶问题。
- **怎么做：** 新增第 5 个 `memoryMode` 取值 `index`（设置命名空间扩展；默认保持
  `policy-only`，轻量默认值不变）。在 `index` 模式下，每会话冻结快照为每个条目渲染一行
  存在性描述——`<scope>/<category> · <projectName?> · <id> · <内容截断至约 80 字符>`——
  按相关度排序（当前项目的 `project` 作用域优先，其次 `user`，再次 `global`；同级内按
  `updatedAt` 倒序）。当预算（`memoryCharLimit`）耗尽时，尾部条目折叠为类别级汇总行
  （`project/convention ×12`），使索引大小随*类别数*而非条目数增长——L1 有界性不变量。
  模型随后沿 索引 → `memory_get(id)` / `memory_search` 路由：LLM 充当解码器。渲染是
  `context/` 中基于现有 `WeakMap` 冻结快照的纯函数——KV 缓存前缀稳定性不变——同一渲染器
  还被 §3.4 的裁决提示词紧凑复用。
- **完成标志：** `index` 模式在 `memoryCharLimit` 下确定性渲染；冻结快照不变量与前缀
  稳定性保持；在一个脚本化会话中，模型*通过读索引并调用 `memory_get`* 找到已存事实
  的测试通过。

### 3.13 准入纪律："No Execution, No Memory"（无执行，不记忆）— P1 — ✅ 已实现（`f5bfecc`）

- **为什么：** 关键词信号 + 阈值提取会收录 LLM 认为"有趣"的一切；垃圾入库目前只能靠
  §3.4 事后兜底。质量关口应当设在写入时。
- **怎么做：** 提取/冲刷提示词采纳排除清单与执行规则：瞬态状态、一次性事件、未验证假设
  一律不持久化；流程型记忆（"如何做 X"，包括故障绕行与工具怪癖）仅当该动作在会话内被
  工具执行验证过时才可准入。新增可选的 `procedure` 类别取值（枚举加法变更、向后兼容）
  标记流程型记忆，供 §3.3 与 §3.12 差异化排序/汇总。提示词变更由 §3.1 回归框架把关。
- **完成标志：** 一个包含琐碎闲聊加一条经执行验证的流程的脚本化会话，只提取出该流程，
  且作用域/类别正确；黄金集拒绝未验证假设行；已有条目在扩展后的枚举下依然有效。

### 3.14 轨迹中的记忆活动 — P1 — ✅ 已实现（`f5bfecc`）

- **为什么：** 用户应在会话轨迹中按需看到记忆的读写过程——一次检索命中了哪些记忆、写入了
  什么——而不必展开原始工具 JSON。
- **怎么做（工具卡片，插件侧，独立交付）：** 为六个工具补充 `presentResult` +
  `output.presentationMeta`，使结构化数据在重放中存活：`memory_search` 获得
  `kind:'search'` 调用卡片（标题 = 查询）与 `card:'search'` 结果卡片（条目作为匹配分组，
  截断并显示总数——fs `grep` 的模式）；`memory_add` / `memory_replace` 获得预览内容
  （前 ~80 字符）的调用卡片，以及带 作用域/类别/id 的结果卡片；`memory_remove` /
  `memory_get` 保持紧凑的通用卡片。这覆盖了轨迹中全部模型发起的读/写，且无需任何宿主改动：
  工具调用默认就渲染在聊天轨迹中，展示器（presenter）是 `defineTool` 的 API 一部分。
- **推迟（需要宿主改动——§6.1/§6.2）：** *聊天流*内的记忆行（为 `memory/*` 会话事件注册
  `ConversationNodeDefinition`）与轨迹表专属行（`ui-trajectory` 的 `TrajectoryCellKind`
  是封闭集）。两者都受会话事件发出阻塞项（§5）制约。§3.8 活动面板在聊天流之外覆盖提取
  写入的可见性缺口。
- **超出范围：** 逐条目定制卡片（`ToolResultView` 联合是封闭集）；经 §3.8 客户端 bundle
  注册自定义 `tool.call.toolview` React 行是可行的插件侧后续项。
- **完成标志：** 页面刷新/重放后卡片与持久化的 `presentationMeta` 渲染一致；一次命中 3 条
  的检索在轨迹中显示查询与 3 个 id；一次 add/replace 卡片显示所存内容预览与生成的 id。

## 5. 被否决的方向与决策门

以下为 v0.x 线路中考虑过并被否决的方向（GA 指 hello-generic-agent）。仅可经由下述
决策门重议。

| 方向 | 否决理由 |
|---|---|
| **`memory/*` 会话事件发出**（原 §3.2） | 无宿主改动策略。宿主持久化读取路径拒绝重新加载包含仓库外事件类型的日志（白名单 `KNOWN_SESSION_EVENT_TYPES` 只含仓库内声明；`known-event-types` 模块文档化了此"拒绝解析"规则；`SessionEvent.ignorable` 标记是唯一的逃生口，而它是*读取侧*字段——`Session.append` 仅从 `sourceEventSeqs`/`surfaceOp` 构造信封、从不设置 `ignorable`，因此插件追加的任何事件都是 required 事件）；已安装依赖中不存在注册插件事件类型的运行时接缝。一旦发出，受影响会话将**无法恢复**。已由插件自有审计存储（§3.2）+ 活动面板（§3.8）替代；类型声明保留为预留项；仅当上游交付接缝时重开（§6.1）。（早期草稿曾点名 `assertEventsSupported` 与 `PersistenceCoordinatorOptions`；这两个符号在已发布的 `@deepseek-ai/*` 依赖中无法解析——很可能位于未发布的 `dsh-web-app` 层，或在锁定发布线上名字不同。拒绝机制本身真实且有文档；在接线 §3.1 日志卫生用例时，请按真实符号重新 pin。） |
| **Embedding / 向量混合检索**（原 §3.3） | 与设计文档自身的规模论证相矛盾（n = 几十到几百条；O(n) 扫描即可，无需索引）。在此规模上，它用一张新 `embeddings` 表 + 域迁移、向量缓存、以及一个 embedding 源决策（要么把 provider 路由耦合进 `MemoryStore` 接缝，要么增加宿主依赖）只换来边际召回。组织良好的非 embedding 检索已实证在可比规模上击败 embedding 系统（Mem0、A-MEM）。 |
| **插件内归档层**（GA L4） | 宿主的会话日志就是归档；冲刷路径已在压缩/销毁时挖掘它们。第二份副本违反"消费而非重造"。 |
| **每轮工作记忆锚点**（GA） | 会话内上下文管理是宿主压缩/投影的职责；每轮注入会破坏每会话冻结快照 / KV 缓存前缀稳定性不变量。 |
| **文件式 L2/L3 物理分层**（GA） | `storage-domain` + 六个工具是正确的物理底座。事实/流程的区分在*逻辑*上采纳（`procedure` 类别 + 准入规则，§3.13），而非重构存储。 |

**不可交易的既有优势。** 任何未来重设计必须保留：所有写入路径上的失败关闭扫描；每会话
冻结快照（KV 缓存前缀稳定）；有界、事件驱动、复用会话 provider 路由的提取（无额外 key
或计费通道）；`MemoryStore` 契约作为消费者与后端之间的唯一接缝。

**语义检索的决策门。** §3.7 遥测记录零结果检索（query、生效的过滤器、次数）。语义检索
只有在 §3.3 + §3.12 落地后、持续的真实世界未命中率证明词法 + 索引召回已饱和时，才允许
重新提案——即便如此，也必须是宿主提供的、可选的 embedding 服务。向量永不在包内内置。
同一无宿主改动策略约束一切会话日志写入：任何未来把插件数据写入会话事件日志的提案，
必须先指明使其安全的宿主接缝（§6.1），并以 §3.1 日志卫生用例证明。

## 6. 宿主约束（无宿主改动策略）

**策略：v0.x 绝不修改宿主代码库。** §3.8/§3.14 提到的所有插件侧接缝（客户端模块表、
`@Remote` 网关、会话节点装配、`presentResult`/`presentationMeta`）都是按文档消费的现成宿主
能力——零宿主改动。下表列出*需要*宿主改动才能实现的能力；每一项都有插件侧替代或明确超出
范围。本表没有任何一行是 v0.x 的依赖。

| # | 被阻塞的能力 | 为什么需要宿主改动 | 插件侧替代 / 状态 |
|---|---|---|---|
| 6.1 | 向会话日志发出 `memory/*` 事件 | 持久化读取路径拒绝含白名单外类型（`KNOWN_SESSION_EVENT_TYPES` 只含仓库内声明）的日志；`Session.append` 仅从 `sourceEventSeqs`/`surfaceOp` 构造信封、从不设置读取侧 `ignorable` 标记，故插件追加的事件恒为 required；已安装依赖中无运行时注册接缝。（早期草稿曾点名 `assertEventsSupported`/`PersistenceCoordinatorOptions`；两者在已发布依赖中无法解析——在新增 §3.1 护栏时请按锁定 dsh 发布线上的真实符号重新 pin。） | 插件自有审计存储（§3.2）+ 活动面板（§3.8）。类型声明保留为预留项；仅当上游交付接缝时重开——可选，永不是依赖。 |
| 6.2 | 聊天流/轨迹表中的记忆行 | 依赖 6.1（聊天节点），或需扩展 `ui-trajectory` 的封闭 `TrajectoryCellKind`。 | 工具卡片（§3.14）在轨迹中展示模型发起的读/写；§3.8 活动面板覆盖提取写入。 |
| 6.3 | apiproxy `RpcMethodMap` 中的 `memory.*` 域 | `RpcMethodMap` 是宿主 apiproxy 的封闭注册表。 | 回环（本地 web 应用）访问今天经 `@Remote` 网关即可用；远程/headless 浏览器超出 v0.x 范围。 |

版本规则：插件消费的每个宿主接缝都锁定到提供该接缝的 dsh 发布线（包已通过 peer 范围跟随
 dsh 发布线）；本表能力只有在对应接缝确实交付的发布线上才可重开，并以 §3.1 集成用例验证。

## 7. 所有演进工作的交叉约束

1. 不破坏四行 bundle 形态；在现有导出子路径内演进。
2. 新设置以安全默认值扩展 `memory` 命名空间——存量用户升级不受影响。
3. 每个新写入路径都经过 `scanContent`。
4. 新注入内容计入 `memoryCharLimit`；每会话冻结快照不变量（KV 缓存前缀稳定）保持。
5. 后台工作（提取、去重裁决、清道夫、迁移）是尽力而为（best-effort），绝不阻塞 agent
   循环。
6. `MemoryStore` 契约保持为消费者与后端之间的唯一接缝。
7. 不引入 embedding 模型、向量索引或包内语义检索：检索保持为对结构化条目的词法检索。
   语义检索若经 §5 决策门批准，只能是宿主侧的可选服务。
8. 无宿主改动：v0.x 既不修改也不假设宿主代码改动；被宿主阻塞的能力（§6）以插件侧替代
   替代或明确推迟，且插件绝不把插件数据写入会话事件日志（§3.1 日志卫生用例是护栏）。
